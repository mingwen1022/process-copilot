# 流程助手（我的流程页 · 待办副驾）· 功能定义与设计

> 定位：我的流程页的**列表级决策支持副驾**。不是又一个通用问答，而是把用户手上一堆流程
> **理清 → 排序 → 体检 → 备选处置**。两层（列表级 ↔ 单据级），双角色（审批人 + 发起人）。
> 是原型审计里认定的最后一块后端缺口（现为纯 UI 占位）。

## 0. 一句话定义

**跨实例的个人流程助手**：审批人侧（待我审批）= 汇总 + 急件排序 + 审批协助；发起人侧（我发起的）= 进度追踪 + ETA。
沿用全项目纪律：**LLM 只理解意图/组织语言，能判对错的（排序、体检、违规、进度、ETA）全是确定性代码**。

## 1. 两层 + 双角色

- **列表级**（流程助手）：跨单汇总、急件排序、路由。对齐"我的流程列表"。
- **单据级**（钻入某单）：审批协助（审批人）/ 进度详情（发起人）。对齐"点行进详情"。
- **双角色**：待我审批（审批人视角，含审批协助）+ 我发起的（发起人视角，进度/ETA）。这是它比运维/发起副驾多出来的**审批人视角**。

## 2. 能力清单与确定性拆解

| 能力 | 角色 | 谁做（LLM 只组织，代码判对错） | 复用 / 新增 |
|---|---|---|---|
| **急件排序** | 审批人 | 确定性 ranker：SLA 剩余 / 停留时长 / 截止时间 算 urgency 分排序 | 🆕 轻 |
| **主动汇总** | 两者 | 确定性计数（5待批/2紧急/3发起/1卡住）+ LLM 只措辞 | 🆕 轻 |
| **审批协助** | 审批人 | ①材料齐否 ②合规红线 ③内容风险 ④LLM 摘要 ⑤批准/驳回=人点 | 多为复用，见 §3 |
| **进度追踪** | 发起人 | 确定性：当前 node + 从当前节点按字段值 `condition_eval` 走剩余路径 | 复用 `preview_path` |
| **ETA 预估** | 发起人 | 确定性：剩余各环节历史平均停留求和 | 复用分析 `node_metrics` |

## 3. 审批协助拆开：大部分是复用

- **①材料齐否** → 复用 `task_inspection`（已建：附件 `required_condition` 走 `condition_eval`）。
- **②合规红线** → 复用模块3 合规引擎（已建）。
- **③内容风险**（如"酒店 1000/晚 超差旅标准 800"）→ **新增，见 §4**。
- **④LLM 摘要** → 把表单明细组织成一句话（组织语言）。
- **⑤批准 / 驳回** → **human-in-the-loop**：助手只摘要 + 标风险 + 给备选，**批准/驳回由审批人点**，点了才触发 slice1 的真实审批动作。**助手绝不自动批。**

## 4. 内容风险检查：值阈值 CheckKind + evaluator + retrieve-then-read

纪律与反哺侧的"结构化 + 代码验证"一致——**LLM 组织，代码判违规**：

```
代码按 (流程/分类/字段) 用 RAG 检索这单适用的制度规则   ← retrieve-then-read（非 tool）
   ├─ 结构化"值阈值"原子规则（新增一种 CheckKind）：
   │     {field:"酒店/晚", op:"<=", threshold:800, condition:"出差城市=一线则1000"}
   │        → 喂【确定性 evaluator】比对表单实际值 → 越界 flag（写法同 condition_eval）
   └─ 原文 chunk → 注入 prompt 给【LLM】组织摘要/引用出处
```

- 新增工作：一种**"值阈值" CheckKind** + 一个**确定性 evaluator**；把差旅标准这类制度阈值**结构化**进原子规则。
- **RAG 是 retrieve-then-read，不是 LLM tool**：①内容风险判定是确定性的（值 vs 阈值），规则必须交**代码 evaluator**，不是丢 LLM 读 chunk 自己想；②代码控制检索范围，LLM 不乱检索/幻觉；③与模块3 全线一致。LLM 只在"组织摘要/引用"处碰 RAG 结果，**不碰"违不违规"**。

## 5. 架构形态：LangChain 结构化提案 + 代码执行（**不用 LangGraph**）

与 `analytics_query_agent` / 运维单轮同一条脊柱：

```
[代码] 预算确定性事实：worklist 排序、各单 task_inspection/内容风险体检、进度/ETA
   │
[LLM] 读用户诉求 → 出结构化意图（AssistIntent：汇总 / 审批协助(item) / 进度(item) / …）   ← LLM 步①
   │
[代码] 执行对应确定性能力（体检/进度/ETA/排序）
   │
[LLM] 组织答复 + 摘要（结构化输出，带备选按钮）                                          ← LLM 步②（可与①合并）
   │
[代码] 批准/驳回按钮 → 触发 slice1 真实审批
```

**为什么不用 LangGraph**：至多两个 LLM 步（意图 + 措辞），固定顺序、无分支/中断/复杂状态，其余全确定性代码 → 够不上。
需要多轮迭代时扩成**有界结构化循环**，仍不改框架。

## 6. 复用 vs 新增（工作量比想象小）

- **复用**：worklist 数据（slice1 工作台桶）、`task_inspection`（材料+合规）、合规引擎、真实审批动作、规则 RAG、`preview_path`（剩余路径）、分析 `node_metrics`（ETA）。
- **新增**：①急件排序 ranker（确定性，轻）②主动汇总（LLM 措辞，轻）③**内容风险："值阈值" CheckKind + evaluator + 制度阈值结构化**（最重）④列表级对话编排（胶水）。

## 7. 反哺延伸：它也是"审批人侧问题暴露点"

审批人**反复在某环节驳回 / 反复要求补同一材料**，与运维反复卡住同构——可作为**审批人侧反哺信号**（结算成一条 incident，过闸聚合 → ProcessInsight，见反哺闭环设计）。这样运维（发起人侧）+ 流程助手（审批人侧）都是反哺暴露点，对称。**先标注，后做（P3）。**

## 8. 分期

- **P1（便宜、可见，多为复用）**：急件排序（确定性）+ 主动汇总（LLM 措辞）+ 进度/ETA（复用 preview_path + node_metrics）+ 单据级复用 `task_inspection`。**很快出可用版本。**
- **P2（重）**：内容风险——"值阈值" CheckKind + evaluator + 差旅标准这类制度阈值结构化 + retrieve-then-read 接入。
- **P3**：审批人侧反哺（反复驳回/补件 → 洞察）。

## 9. YAGNI / 边界

- 助手**只做决策支持**：摘要、排序、体检、备选；**批准/驳回永远人点**（human-in-the-loop）。
- 排序/进度/ETA/违规**全确定性**；LLM 只理解意图 + 组织语言，不碰判断。
- 内容风险只覆盖**能结构化成"值阈值"**的制度；化不成的（纯定性条款）不硬做。
- 不引入 LangGraph；不做自主 tool-calling；RAG 走 retrieve-then-read。
