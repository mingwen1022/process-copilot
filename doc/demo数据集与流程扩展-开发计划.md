# Demo 数据集与流程扩展 · 开发计划

> 目标:把 demo 从"单一请假流程"扩成"多流程、可发起、可点进看单据"的完整形态,让四模块闭环(设计→流转→分析→反哺)和各 agent 场景都有足够的测试数据支撑。
> 定稿日期:2026-07-10。本文是执行蓝图,分 P1–P4 四期,每期可独立验收。

---

## 0. 定位:两条轴 + 三档深度

一个流程能"深"的方向有两条,成本差很多,**不该每个流程两轴做满**:

- **设计轴**:`data/cases/{流程}/raw_sources/`(多格式带噪声源文档)+ `standard/target.json`(金标准定义 + 澄清目标 + 评分权重)→ 喂设计初始化 + extraction eval。**成本高**(手写逼真矛盾/噪声源 + 带 rubric 的 gold)。
- **运行轴**:live 定义(可复用 gold)+ `InstanceContext` mock 实例 + 可选合成分析事件 → 喂发起/待办/运维/分析/反哺。**成本中**。

### 目标覆盖矩阵

| 流程 | 设计源 | 设计 def | eval | 运行实例 | 分析样本 | 发起/流程管理 | 定位 |
|---|---|---|---|---|---|---|---|
| **请假** | ✅ | ✅ | ✅ | ✅ | ✅ 600 | ✅ | 运行锚(已完成) |
| **EOA140 子公司重大事项** | ✅ | ✅ | ✅(94.21) | ➕ 少量 | — 不做 | ➕ 补 | 设计锚 + 补最小运行,演"设计→上线" |
| **费用报销** | ➕ 全补 | ➕ | ➕ | ➕ | ➕ 合成 | ➕ | 第二条全套 · 内容风险样板 · 分析双流程 |
| **采购 / 用印** | ➕ 轻源 | ➕ 轻 def | — 不做 | — 不做 | — 不做 | ➕ 轻 | 广度 · 目录级(可设计可发起,不做深) |

**三档定位一句话**:请假管运行、EOA140 管设计(补最小运行)、报销做第二条全套、采购/用印撑广度。

### 关于 llm_lora / CORD(已决:不做)

llm_lora 是"不规则文本→结构化"的抽取微调研究,与本项目"标准化表单流转"任务目标不同。**本期不做"上传发票自动解析"功能**,报销字段按真实报销单常识配置,不攀 CORD。两个项目在 portfolio 里作为独立但主题相关的作品。上传解析作为未来可选加分项(需自托管 vLLM,与低成本部署冲突),不在本计划内。

## 1. 贯穿原则(所有期共用)

- **发起页能发起的 = 流程管理里有定义的**。两页共享同一份流程 catalog,不再出现"发起页有壳、流程管理没有"的错位。
- **实例详情 = 回放设计好的 OA 要素**。点进发起/我的流程任一实例,主区展示我们在设计工作台定义的:表单(字段+值)、审批意见(opinion_label+结论)、提交路径(条件+目标环节)。
- **提交流转做成演示态**。点"提交/通过"→ 弹提示"仅供演示,暂不支持实际流转",不推真实引擎。
- **运行轴不配 eval**。流转/诊断正确性靠确定性引擎 + 现有 313 单测保证;只有设计轴有 gold eval(target.json)。
- **轻量流程注册表(P2 起建立)**:一个流程的类型/定义/实例目前散在 `launch_catalog.py` / `mock_instances.py` / `todo_service.py` 三处。P2 加 EOA140 时顺手建立"一个流程声明一次、三处派生"的模式,避免漂移;P3/P4 沿用。不做大重构,只在新增流程时走新模式。

## 2. 分期计划

### P1 · 发起页接通 + 实例详情 OA 要素回放(小,不依赖新数据)

**为什么先做**:纯前端 + 复用现有请假定义/API,不等任何新数据;做完就能点进每个流程看到完整单据视图,是后面所有流程共用的"壳"。

**任务**:
1. **发起卡片可点** — `renderLaunch()` 给每张卡加 onclick → 打开发起单据填写页。
2. **发起单据填写页** — 新增 `pg-launch-form`(或复用详情页布局):
   - 拉 `GET /workflows/{workflow_definition_id}/launch-form` 得 `form_schema` + `initial_values`,渲染可填表单(请假流程实测可用)。
   - 无定义的流程(采购/用印在 P4 前)显示"该流程 demo 暂未开放发起"。
3. **实例详情补 OA 要素** — 现 `pg-my` 只有流转位置/表单/诊断;补:
   - **审批意见区**:各审批环节的 opinion_label + 结论选项(同意/不同意)。
   - **提交路径区**:该单据当前环节的 submit_paths(条件 + 目标环节),复用 designws 里 `dw-nodes` 的 path-item 样式。
4. **提交演示态** — 发起页"提交"、详情页"通过/退回"→ 统一弹 toast"仅供演示,暂不支持实际流转"。

**验收**:发起页点任一(有定义的)流程 → 填表单 → 提交弹演示提示;我的流程点任一实例 → 看到表单+意见+路径的完整单据视图。

### P2 · EOA140 补运行轴(中)

**为什么**:EOA140 是设计锚(94.21),但运行侧全空。把它的 gold 定义载入 runtime + 少量实例,就能演"在一个**复杂难流程**上,从设计工作台设计好 → 上线 → 在流程管理/我的流程里可见"——这是四模块闭环里目前最缺的"设计→上线"握手展示。

**任务**:
1. **gold def 载入 runtime** — 从 `data/cases/EOA140_subsidiary_major_matter/standard/target.json` 取 `deterministic_process_definition`,写一个 seed 脚本(参考请假如何进 `workflow_definitions` 表)插入为 live 定义(status 可设 PUBLISHED 或 DRAFT)。
2. **建立流程注册表模式** — 新增一个轻量 seed 模块(如 `app/copilots/demo_processes.py`),声明 EOA140 的:catalog 条目 + 1–2 个 mock 实例;`launch_catalog` / `mock_instances` / `todo` 从它派生。
3. **少量 mock 实例** — 2 个 `InstanceContext` 实例(如"某子公司重大事项审批中""会签待某部门"),供我的流程展示 + 运维诊断可选。
4. **发起接入** — EOA140 进发起 catalog,可走 P1 的发起表单。

**验收**:流程管理出现 EOA140 卡片(已发布/草稿);发起页可选 EOA140;我的流程有 EOA140 实例可点进看单据。

### P3 · 费用报销全套(大,价值最高)

**为什么**:第二条全套流程。让内容风险审批协助踩在真流程上;让运行数据板块支持**两流程对比**(可测的分析方向翻倍);报销是最贴近 fintech 岗位的场景。

**报销流程设计(字段/环节/路径)**:
- **表单字段**:报销人(系统只读)、所属部门(系统只读)、费用类型(下拉:差旅/招待/办公/培训)、出差城市(差旅时)、费用明细(子表:项目/日期/金额)、报销总额(自动汇总)、酒店每晚 & 机票金额(超标检测用)、关联发票(附件·必传)、事由(多行文本)。
- **流程环节**:起草 → 部门主管审批 →〔金额分级〕财务初审 → 财务负责人审批 → 结束。
- **提交路径(核心逻辑=金额分级)**:总额 < 5 万且主管同意 → 结束;总额 ≥ 5 万 → 财务初审 → 财务负责人;不同意 → 退回起草。
- **附件条件**:发票必传;酒店/机票超标准 → 需附情况说明(挂现有内容风险规则)。

**任务**:
1. **设计 case** — `data/cases/expense_reimbursement/`:
   - `raw_sources/`:差旅费报销制度(含酒店/机票标准)、财务审批权限矩阵(金额分级)、票据明细样例、群聊噪声、上线待确认清单(多格式,带矛盾)。
   - `standard/target.json`:金标准 def + clarification/guardrail + eval_weights(见 §3)。
2. **live def 载入 runtime**(复用 gold,同 P2 seed 模式)。
3. **mock 实例** — 3 个:正常报销 / 酒店超标(触发内容风险审批协助)/ 大额待财务(走分级路径)。对齐现有待办里的 `ap_expense_wang`。
4. **内容风险规则落地** — 确认 `差旅超标` 规则(酒店 800/晚上限等)指向报销真实字段,审批协助踩在真 def 上。
5. **合成分析事件** — 参考 `scripts/gen_leave_process_event_log.py` + `run_leave_process_metrics.py`,生成报销的合成事件日志与指标;运行数据板块加流程切换,支持请假/报销两套画像对比。
6. **eval 接入** — target.json 进 eval harness(`app/eval/batch_eval.py`),报销成为第三个 extraction eval case。

**验收**:报销可设计(设计工作台读真 def)、可发起、我的流程有实例;审批协助对超标实例给真实风险提示;运行数据板块可切到报销看不同画像;eval 能跑报销 case 出分。

### P4 · 采购 / 用印 轻设计(中小)

**为什么**:发起页/流程管理要体现广度,但不值得做深。给它们最小设计资产,让两页都成立、可"设计"可"发起"。

**任务**:
1. **轻源 + 轻 def** — 各配一份简单 `raw_sources/`(1–2 篇)+ 可产出的 process def(环节少,如:起草→审批→〔高风险〕法务/委员会→结束)。
2. **进 catalog + runtime** — 走 P2 注册表模式,进流程管理(草稿态)+ 发起 catalog。
3. **不做**:运行实例、分析、eval。

**验收**:流程管理/发起页出现采购、用印卡片;可点进设计工作台看其(简单)定义;可走发起表单(演示态)。

## 3. 报销 eval 字段设计

沿用现有 8 维权重结构(请假现值:`meta:5 / form_fields:20 / flow_nodes:15 / submit_paths:20 / attachments:5 / roles:5 / clarifications:20 / evidence_guardrail:10`,合计 100),按报销重心调整:

| 维度 | 请假 | 报销建议 | 理由 |
|---|---|---|---|
| form_fields | 20 | **25** | 报销字段多(明细子表/金额),抽取更难 |
| submit_paths | 20 | **25** | 金额分级路径(≥5 万加财务)是核心逻辑 |
| attachments | 5 | **10** | 发票必传 + 超标附说明,附件条件是重点 |
| flow_nodes | 15 | 10 | 报销环节比请假简单 |
| clarifications | 20 | 20 | 见下 |
| meta / roles / evidence_guardrail | 5/5/10 | 3/2/5 | 相应下调,凑 100 |

**报销特有 clarification_targets**(源里故意留的模糊点,考 pipeline 会不会问):
1. 差旅超标怎么处理?(超标准 → 附情况说明 / 硬拦 / 升级审批)—— severity: blocking
2. 大额分级阈值是否明确?(源给区间还是要问,如"≥5 万加财务负责人")
3. 费用明细必须逐项录入还是只填总额?

**报销 guardrail_targets**(不该臆造):源里没写死的金额阈值不能自己编;"建议"的审批环节不能当强制。

## 4. 建议执行顺序

1. **P1 先做**(小、立刻能点、不依赖新数据)——把"壳"打好。
2. **P3 报销**(价值最高:第二条全套 + 内容风险落地 + 分析双流程)。
3. **P2 EOA140 运行轴** 与 **P4 采购/用印** 相对独立,可后置、可穿插。

每期做完独立验收、独立 commit,不 push。涉及 DB 写入(P2/P3 seed 定义)前先备份 `data/runtime/runtime.db`。真实源文档/公司制度只作形状参考、不入库,合成语料标 `synthetic:true`。
