# 企业级流程设计 Agent Demo —— 项目整体计划

> 版本：V1.1 | 日期：2026-05-08 | 状态：规划中

---

## 一、项目背景与目标

### 背景

在企业流程线上化工作中，流程设计人员需要从多个零散信息源（文档、表格、邮件、即时消息、会议纪要等）中收集业务需求，手工整理成标准化的**线上流程要素管理文档**，再交给开发人员进行系统实现。这一过程耗时、易出错、高度依赖人工经验。

### 项目目标

构建一个基于 **LangChain + LangGraph** 的流程设计 Agent，自动完成：

1. **信息整合**：从多个异构信息源中提取流程需求信息
2. **缺失检测**：识别信息不完整或冲突的要素，主动向需求方询问补充
3. **标准化输出**：生成符合企业规范的标准化流程要素文档（JSON + 可读表格/流程图）

> **第一版本 Demo 聚焦**：多信息源整合 → 标准化文档生成（暂不涉及开发、测试、上线、优化环节）

## 二、参考文档说明

| 文件名 | 用途 |
|--------|------|
| `XXX线上流程要素管理文档（流程管理申请）.xlsx` | 标准模板，定义所有要素字段及说明 |
| `参考样例-互联网应用对外发布线上流程要素管理文档.xlsx` | 已填写的完整样例，用于理解真实要素写法 |
| `某券商电子公文系统使用管理办法.doc` | 系统级平台规范（Demo 阶段参考，非主要约束） |

### 模板核心结构（7个维度）

1. **流程表单配置**：定义表单中每个字段的名称、组件类型、必填规则、可见/编辑权限、逻辑联动
2. **流程图**：审批流转路径示意
3. **流程环节配置**：每个审批节点的处理人规则、意见要求、提交路径及条件
4. **附件说明**：附件类型、上传环节、必传规则
5. **角色配置**：流程中涉及的自定义角色及挂接人员
6. **需求填写说明**（模板辅助页）
7. **流程表单示意图**（原型图）

## 三、第一版本 Demo 范围

### 3.1 精简标准要素（核心字段）

第一版 Demo 去除高复杂度内容（风险点、运维要求、外部系统关联），保留以下核心要素：

#### 表单要素（FormField）

| 属性 | 说明 |
|------|------|
| `field_name` | 字段名称 |
| `required_stages` | 必填环节列表 |
| `visible_stages` | 支持查看的环节列表 |
| `editable_stages` | 支持编辑的环节列表 |
| `component_type` | 组件类型（单行文本/多行文本/下拉单选/下拉多选/日期/员工选择/部门选择/数字等） |
| `logic_description` | 字段显示/联动逻辑说明（可选） |
| `default_value` | 默认值（可选） |
| `options` | 下拉选项列表（可选，适用于下拉组件） |

#### 流程环节要素（FlowNode）

| 属性 | 说明 |
|------|------|
| `node_id` | 环节唯一标识 |
| `node_name` | 环节名称（如"部门主管审批"） |
| `handler_mode` | 处理人选择方式（单选/多选-并行/多选-抢办/全选-并行/全选-抢办） |
| `handler_source` | 处理人部门来源（本部门/本公司/特定部门/不指定） |
| `handler_role` | 处理角色（通用角色或自定义流程角色） |
| `opinion_type` | 意见类型（结论性必填/结论性非必填/意见详情必填/意见详情非必填） |
| `opinion_label` | 意见域名称（如"申请部门意见"） |
| `submit_paths` | 提交路径列表（每条路径含路径名称和触发条件） |

#### 角色配置（RoleConfig）

| 属性 | 说明 |
|------|------|
| `role_name` | 角色名称 |
| `role_type` | 角色类型（流程角色/业务角色） |
| `members` | 挂接人员列表 |

### 3.2 Demo 示例流程：请假申请

**流程路径**：起草 → 部门主管审批 → 部门领导审批 → 部门总经理审批

**表单字段设计**（10个）：

| 序号 | 字段名称 | 组件类型 | 必填 | 说明 |
|------|----------|----------|------|------|
| 1 | 标题 | 单行文本 | 起草 | 格式：姓名+假期类型+请假申请，自动生成 |
| 2 | 申请人 | 文本（只读） | 起草 | 自动带出登录人姓名 |
| 3 | 所属部门 | 部门选择 | 起草 | 自动带出登录人所属部门 |
| 4 | 假期类型 | 下拉单选 | 起草 | 选项：年假/事假/病假/调休/婚假/产假/陪产假/丧假 |
| 5 | 开始日期 | 日期组件 | 起草 | 格式：yyyy-MM-dd |
| 6 | 结束日期 | 日期组件 | 起草 | 格式：yyyy-MM-dd；需晚于或等于开始日期 |
| 7 | 请假天数 | 数字（只读） | - | 根据开始/结束日期自动计算（按工作日） |
| 8 | 请假事由 | 多行文本 | 起草 | 字数限制：200字 |
| 9 | 代理人 | 员工选择 | 起草 | 工作期间代理人，仅限本部门 |
| 10 | 紧急联系方式 | 单行文本 | 起草 | 假期期间联系电话 |

**审批路径设计**：

```
起草
  └─ [提交] → 部门主管审批
                ├─ [同意] → 部门领导审批
                │             ├─ [同意，且请假天数≤3天] → 流程结束
                │             ├─ [同意，且请假天数＞3天] → 部门总经理审批
                │             │                              ├─ [同意] → 流程结束
                │             │                              └─ [不同意] → 返回起草
                │             └─ [不同意] → 返回起草
                └─ [不同意] → 返回起草
```

## 四、工程化方案设计

### 4.1 数据结构（Pydantic Schema）

```
ProcessDefinition
├── meta: ProcessMeta                      # 流程元信息（名称、编号、版本、所属系统等）
├── form_fields: List[FormField]           # 表单字段列表
├── flow_nodes: List[FlowNode]             # 审批环节列表
│   └── submit_paths: List[SubmitPath]     # 每个环节的提交路径（含条件）
├── attachments: List[AttachmentConfig]    # 附件配置（可选）
└── roles: List[RoleConfig]               # 角色配置
```

所有 Optional 字段配合 `description` 元信息，支持 LLM structured output 直接生成。

### 4.2 标准化输出的生成关系

**JSON 是唯一数据源（Single Source of Truth）**，所有可读版本均基于 JSON 生成，不单独维护：

```
process_def.json（机器可读，Pydantic 校验）
        │
        ├─── form_fields ──────────────→ Excel（表单配置 Sheet）
        │                                  ↕ 对齐原模板列格式，供需求方确认
        ├─── flow_nodes ───────────────→ Excel（环节配置 Sheet）
        │
        ├─── roles ────────────────────→ Excel（角色配置 Sheet）
        │
        └─── flow_nodes + submit_paths → draw.io XML（由 ArtifactGenerationAgent 调工具生成）
```

> **说明**：V1 不引入 Mermaid 新链路。Excel 由 ArtifactGenerationAgent 调用 xlsx skill tool 生成；
> draw.io 由 ArtifactGenerationAgent 调用 draw.io tool 让 LLM 直接生成 XML，并做基本 XML 校验。

### 4.3 LangGraph 工作流

```
load_case_context
  -> process_extraction_agent
  -> validate_and_compare
  -> artifact_generation_agent
  -> write_run_outputs
  -> END
```

V1 只保留两个真正的 agent：`ProcessExtractionAgent` 与 `ArtifactGenerationAgent`。加载、校验、对比、写报告均为确定性 LangGraph function node。

### 4.4 技术选型

| 组件 | 技术 | 说明 |
|------|------|------|
| Agent 框架 | LangGraph | StateGraph 管理 agent 工作流状态 |
| LLM 调用 | LangChain `ChatBedrockConverse` | 使用 `AWS_BEARER_TOKEN_BEDROCK` 单 Bedrock API key 调 Claude Sonnet 4.6，并保留 LangChain messages/tool calls |
| Schema 校验 | Pydantic v2 | 定义标准要素数据模型，支持 JSON Schema 导出 |
| 信息源解析 | LangChain loaders | TextLoader / UnstructuredWordDocumentLoader 等 |
| Excel 生成 | xlsx skill tool | ArtifactGenerationAgent 调用 LangChain tool，读取本地 xlsx SKILL.md |
| 流程图生成 | draw.io XML tool | ArtifactGenerationAgent 调用 LangChain tool，由 LLM 直接生成 .drawio |
| 测试数据存储 | 本地文件 | txt / json / xlsx，模拟多信息源 |

## 五、测试数据规划（模拟信息源）

### 5.1 流程图绘制原则

**关键分叉定义**：同一份申请因某个业务属性不同，走向**完全不同的审批链路**，才在 draw.io 流程图中画为菱形判断节点。典型例子：
- 开票流程按"信用业务类型"分叉为质押业务路径 vs 融资融券路径
- 设备出库按"申请人身份"分叉为总部IT / 资管子公司 / 分公司等不同审批链
- 用印申请按"印章类型"分叉为法务路径 vs 财务路径

**不画进流程图的内容**（归表格管理）：
- 每个节点的同意→下一环节、不同意→退回起草
- 具体路径控制条件表达式
- 限时处理、意见必填等配置细节

### 5.2 测试流程设计（4个）

共设计4个测试流程，每个包含 raw_sources（模拟零散信息源）+ standard（标准化输出）：

#### ① 请假申请
- **流程结构**：简单线性，天数判断为小分叉（天数 ≤3天止于部门领导，>3天继续报总经理）
- **覆盖模式**：baseline，线性流 + 轻度分叉
- **流程图形态**：无关键分叉菱形，纯节点序列
- **信息源噪音设计**：

| 问题类型 | 具体内容 | 出现位置 |
|----------|----------|----------|
| 信息缺失 | 未提及"代理人"字段 | 需求文档、消息 |
| 信息冲突 | 天数门槛：一处说"3天"，一处说"5天"需总经理审批 | 消息周五 vs 邮件 |
| 表述模糊 | "领导审批"未区分部门领导还是总经理 | 会议纪要 |
| 字段逻辑缺失 | 假期类型选项列举不全（只提了年假、事假） | 消息周一 |

#### ② 费用报销申请
- **流程结构**：报销金额为关键分叉——≤5万：部门主管→部门负责人→财务确认；>5万：部门主管→部门负责人→财务初审→财务负责人审批
- **覆盖模式**：数字字段触发关键分叉、财务类固定角色
- **流程图形态**：1个关键分叉菱形（金额判断），两路后汇回财务确认节点
- **信息源噪音设计**：

| 问题类型 | 具体内容 | 出现位置 |
|----------|----------|----------|
| 信息冲突 | 金额门槛：消息说"5万"，邮件说"3万"，需求文档未写 | 三个来源不一致 |
| 角色缺失 | 财务确认人员只知道"财务部的人"，具体角色未指定 | 消息、会议纪要 |
| 字段逻辑缺失 | 费用类别选项不完整（只提了差旅、办公用品） | 需求文档 |
| 附件要求缺失 | 是否需要附发票扫描件未提及 | 所有来源 |

#### ③ 用印申请
- **流程结构**：印章类型为关键分叉——公章/合同章：法务审核→行政管理部审批→印章管理员办理；财务专用章：财务部审核→印章管理员办理；两路均结束于归还登记知悉
- **覆盖模式**：业务类型触发关键分叉（最接近附件参考图结构）、特定职能部门角色、附件必传
- **流程图形态**：1个关键分叉菱形（印章类型），两路后汇回印章管理员节点
- **信息源噪音设计**：

| 问题类型 | 具体内容 | 出现位置 |
|----------|----------|----------|
| 路径冲突 | 法务和行政审核顺序：消息说"先法务"，邮件说"先行政" | 消息 vs 邮件 |
| 角色缺失 | 印章管理员只知道"行政那边管印章的"，无具体角色名 | 需求文档 |
| 字段缺失 | "用印事由"字段未提及是否必填 | 消息、会议纪要 |
| 附件要求模糊 | 提到"要附材料"但未说明是合同原件还是扫描件 | 会议纪要 |

#### ④ 采购申请（简化版）
- **流程结构**：申请部门内部审批（经办人→部门主管→部门负责人）→采购部门受理处理→双方确认回签；采购金额≥50万时增加采购委员会会签（并行）
- **覆盖模式**：跨部门双向流转、并行会签、金额门槛触发额外环节
- **流程图形态**：1个关键分叉菱形（金额≥50万触发委员会会签），并行节点并拢后汇回确认
- **信息源噪音设计**：

| 问题类型 | 具体内容 | 出现位置 |
|----------|----------|----------|
| 信息冲突 | 委员会会签门槛：需求文档"50万"，消息"30万" | 需求文档 vs 消息 |
| 流程结构模糊 | "采购部门审核完让我们确认"—不清楚是否需要申请方回签环节 | 会议纪要 |
| 角色缺失 | 采购委员会成员未说明，只说"走委员会" | 所有来源 |
| 字段缺失 | 供应商信息字段完全未提及 | 需求文档、消息 |
