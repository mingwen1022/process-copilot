V2 迭代方案 - 组织规则驱动的流程运行沙盒

目标是在现有流程设计 Agent 之上，增加虚拟券商组织架构、规则知识库和简易审批运行时， 验证 ProcessDefinition 是否能够驱动可发起、可审批、可流转、可回放的实际流程。

1. 研究结论与产品判断

组织 券商组织模拟

证券公司前台通常按客户或业务类型设置，例如零售/经纪、财富管理、机构业务、投资银行、 证券投资、资产管理等；管理控制部门包括风险管理、法律合规、审计/稽核，后台包括人力、IT、办公室等。

设计上应模拟业务条线、部门、分支机构和三道防线，而不是只做单层部门列表。

运行 先自建轻量运行时

飞书审批有完整用户侧体验和外部审批能力，但 API 创建审批定义存在平台约束，例如官方说明 API 方式不支持设置条件分支。 当前更适合先做本地运行沙盒，后续再做飞书 adapter。

先验证流程定义语义，再考虑企业平台集成。

知识 RAG 约束设计

规则、制度、授权矩阵、组织架构应进入检索层。LangChain 的 RAG 模式把索引和运行时检索分开， LangGraph 可扩展为 agentic RAG，让模型决定何时检索。

流程设计不只看 raw source，还要看公司规则和组织上下文。

产品方向： V2 不做完整 OA，也不直接接入飞书或 BPMN 引擎。先做“流程运行沙盒”，用虚拟组织和规则知识库检验流程设计结果是否可执行。

2. 虚拟券商组织架构设计

组织模型要服务两个目标：一是给流程设计 Agent 提供真实约束，二是给运行沙盒解析处理人。 因此需要同时建模“条线 - 部门 - 组 - 岗位 - 兼任关系”。

华东证券模拟公司 ├── 公司治理层 │ ├── 董事长 │ ├── 总裁 │ ├── 分管领导 - IT条线 │ ├── 分管领导 - 零售/财富条线 │ ├── 分管领导 - 投行条线 │ ├── 首席风险官 CRO │ └── 合规总监 CCO ├── IT条线 │ ├── 信息技术总部 │ │ ├── 总经理 / 副总经理 / 总经理助理 │ │ ├── 应用研发组 - 主管 / 员工 │ │ ├── 数据平台组 - 主管 / 员工 │ │ └── 安全运维组 - 主管 / 员工 ├── 零售与财富条线 │ ├── 财富管理总部 │ ├── 信用业务部 │ └── 分支机构管理部 ├── 投行条线 │ ├── 投资银行管理委员会 │ ├── 投行一部 / 投行二部 │ └── 投行质控部 ├── 机构与交易条线 │ ├── 机构客户部 │ ├── 固定收益部 │ └── 权益衍生品部 └── 中后台与监督条线 ├── 计划财务部 ├── 人力资源部 ├── 行政办公室 ├── 风险管理部 ├── 合规法律部 └── 稽核审计部

建议内置兼任样例

  • IT 条线分管领导兼任信息技术总部总经理，用于测试“上级与部门负责人同人”的去重和升级。
  • 信息技术总部总经理助理兼任数据平台组主管，用于测试组级审批和部门级审批的跳转。
  • 合规总监兼任合规法律部总经理，用于测试合规职能审批。
  • 投行条线分管领导兼任投资银行管理委员会主任，用于测试委员会/条线双重身份。
  • 计划财务部分管领导兼任计划财务部总经理，用于测试财务金额审批升级。

3. 自下而上的流程设计原则与规则/RAG

流程设计不能只按 raw source 描述“画路径”，还要遵守组织层级、授权矩阵、岗位职责和制度边界。 这里建议把“自下而上”固化为一组规则，并让 Agent 通过 RAG 检索制度依据。

层级规则 默认审批链

  1. 发起人提交后，默认先到直属主管或组主管。
  2. 部门内事项进入部门总经理或副总经理审批。
  3. 跨部门、跨条线或高金额事项进入条线分管领导。
  4. 重大事项进入总裁、董事长或专门委员会。
  5. 监督类事项必须引入合规、风险、稽核等独立审核环节。

冲突规则 兼任与回避

  1. 如果下一审批人与发起人相同，必须跳过或升级。
  2. 如果多个连续环节解析到同一人，保留最高必要审批环节并记录原因。
  3. 经办人与复核人不能是同一人。
  4. 合规、风险、财务等独立审核不应被业务条线负责人替代。
  5. 退回路径统一回到 DRAFT 或上一处理人，不能产生孤立任务。

规则知识库范围

规则文档 示例内容 影响的流程设计
组织架构与岗位职责说明 部门职责、条线负责人、部门负责人、兼任关系 处理人来源、角色解析、审批层级
授权审批矩阵 金额、风险级别、业务类型对应的审批权限 金额分叉、升级路径、董事长/总裁审批
财务费用管理办法 报销、预算、付款、采购金额边界 费用报销、采购、付款流程
信息系统变更管理办法 开发、测试、上线、回退、安全评估 IT 发布、权限申请、系统变更流程
印章与合同管理办法 印章类型、法务审核、行政审批、归档要求 用印、合同会签、文件归档流程
电子公文系统使用管理办法 文种类别、办公室枢纽、三级审批、时限、催办、归档 工作签报、发文、收文、公告、制度、合同、用印等通用公文流程

RAG 工作流调整

1. 解析意图 判断 raw source 属于费用、用印、采购、IT 变更、人事等类型。
2. 检索规则 从制度库、组织库、授权矩阵检索相关条款和岗位信息。
3. 抽取流程 ProcessExtractionAgent 同时看到 raw source 和规则上下文。
4. 业务校验 ValidationAgent 检查是否违反层级、回避、金额、职能审核规则。
5. 运行验证 用 runtime sandbox 发起实例，检查处理人、路径、条件是否可执行。
V2 边界： RAG 先支持本地制度 Markdown/TXT 和组织 JSON，不处理复杂 PDF 版式。后续再接 DOCX/PDF 解析和引用级证据展示。

4. 流程开发/运行功能方案

“流程开发”在 V2 中不是代码生成，也不是接入完整 OA，而是把流程库中的 ProcessDefinition 编译为本地可运行实例。用户可以发起、审批、退回、切换审批人，并看到流转日志。

核心功能

功能 说明 验收标准
流程库运行入口 在流程详情页新增“运行流程”或“开发为运行流程”。 从任一流程库流程进入运行沙盒。
表单渲染 根据 form_fields 生成申请表单，支持文本、数字、日期、下拉、员工选择。 字段必填、默认值、选项和只读状态生效。
路径选择 审批人看到当前环节可用的 submit_paths。 路径按钮按条件过滤，不满足条件的路径不可提交或显示禁用原因。
处理人解析 根据组织架构解析部门主管、部门总经理、条线分管领导、特定角色。 能够处理兼任、跳过同人、升级到上级。
当前用户切换 页面顶部提供 Persona Switcher，模拟不同审批人登录。 切换后待办列表和可操作按钮变化。
实例轨迹 记录每次提交、审批、退回、自动跳过和条件命中。 实例详情可还原完整审批路径。
流程图高亮 使用现有 draw.io 或简化 SVG，高亮当前环节和已走路径。 用户可以看出实例当前卡在哪个环节。

运行状态机

DRAFT 申请人填写或被退回修改。
ACTIVE 存在待办任务，等待审批人处理。
RETURNED 退回起草或退回上一处理人。
COMPLETED 进入 END，实例结束。
CANCELED 申请人撤回或管理员终止。

5. 本地数据库方案

V2 建议引入本地 SQLite。理由是审批实例、任务、日志、组织架构和规则元数据都已经具备明显的关系型结构； SQLite 是单文件、零配置、ACID 事务的嵌入式数据库，适合本地 demo 和测试。

V2.1 边界： 组织数据先以 data/org/org_seed.json 作为 canonical source，规则知识先以 data/knowledge/*.md 保存；SQLite 从 V2.2 运行时内核开始引入。

结构化状态 SQLite

  • 保存流程定义版本、运行实例、待办任务、表单值、审计日志。
  • 保存组织架构、岗位任职、兼任关系、角色解析规则。
  • 用 Python 标准库 sqlite3 起步，后续再引入 SQLAlchemy/Alembic。

规则检索 Chroma 或轻量索引

  • 规则文档先落在 data/knowledge/。
  • 如果要做语义检索，可用 Chroma PersistentClient 持久化本地索引。
  • 如果暂时不想增加 embedding 成本，可先做关键词/BM25 + metadata 过滤。
