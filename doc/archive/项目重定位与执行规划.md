## 0. 这份文档要解决的问题

项目在 V1（AI 设计流程）之后，逐步长成了**两个产品**：AI 设计侧 + 一个 mini OA/BPM 运行时平台（登录、工作台、组织架构、审批流转、流程管理……）。运行时越搭越重、偏离主线。

本文的目的：**把主线拉回 AI，保留完整闭环的故事，但把运行时降级为"数据底座"**，并明确砍掉哪些过重功能、保留哪些核心、按什么节奏执行。

---

## 1. 核心重定位

**它不是 OA，而是一个"AI 流程全生命周期闭环 agent"。**

闭环：**AI 设计流程 → 上线流转 → 运行数据的提效/堵点分析 → 优化建议反哺设计**。

> 关键认知：OA 不是要建的产品，而是**产生"流程运行数据"的底座**。一旦这么看，包袱就卸了——运行时只要能跑通 happy path 并吐出结构化事件日志即可，**不需要组织架构平台/用户体系/工作台全功能**。真正深做的是两端的 AI：**设计侧** 和 **运营分析侧**。

### 1.1 与个人经历的映射（这是项目最强的叙事）

| 闭环阶段 | 对应工作经历 | 项目中的角色 | 深度 |
|---|---|---|---|
| ① AI 设计流程（+规则 RAG） | 流程产品设计 / 线上化 | 护城河① | **深做** |
| ② 流程上线流转 | 移动化审批覆盖 64%→95% | 数据底座 | **薄做** |
| ③ 运行数据→提效/堵点分析 | 流程效能看板、办结时长↓27.9%、识别堵点 | 护城河② | **深做** |
| ④ 优化建议反哺设计 | 推动功能优化迭代提效 | 闭环点睛 | 轻量 |

加上 AI / RAG / Agent / 评测，叙事即：**"我把做了 3 年的流程治理工作，做成了一个能自动设计、运行、并用 agent 持续优化的闭环产品。"**

## 2. 目标架构（4 模块 + 闭环）

```
        ┌──────────── 规则知识库 (RAG) ────────────┐
        │ 公司级/系统级制度 · 流程要素规范 · 模板    │
        └───────────────┬───────────────────────────┘
                        │ 检索"适用规则"作为设计约束与依据（并用于合规评测）
   多源需求 ──▶ ① 设计 Agent ──▶ 标准流程定义(JSON) + Excel/drawio
                        │              │ 评测：要素级准确率(对 gold) + 规则合规率(无参照)
        对话式修改 ⟲────┘              ▼
                            ② 薄运行时(happy path) ──▶ 结构化运行事件日志
                                     │   (+ 合成事件日志生成器批量造数据)
                                     ▼
                            ③ 运营分析 Agent ──▶ 效能指标(时长/人工介入/停滞/退回) + 堵点 + 优化建议
                                     │
                                     └────▶ ④ 优化建议反哺 ① 重新设计  ⟲ 闭环
```

两个把"主线拉回"的关键设计：

1. **运行时只产数据，不做平台**：现有 runtime 跑通 1–2 条 happy path 产生真实实例；其余靠**合成事件日志生成器**按流程定义批量造（注入真实分布：某环节慢/某环节退回多/某处人工介入）。分析 agent 要的是**数据**，不是完整 OA。
2. **规则 RAG 与 source 摄取分离**：
   - **source 摄取** = "这一条流程的需求"（多源、单流程输入）。
   - **规则 RAG** = "跨流程的公司制度/规范"（知识库，约束所有流程设计）。
   - 顺带：规则 RAG 同时是个**生产级 RAG 作品**，补齐简历里 RAG 这块短板。

## 3. 模块详解（定位 / 要做什么 / 停止线）

### M1 · 设计 Agent + 规则 RAG（护城河①，深做）

- **现状**：source 摄取（含修复/证据索引/质量发现/parser 建议）→ 抽取 → 结构校验 → 业务校验 → 评测 → 设计产物(JSON+Excel+drawio)。6 个真实企业流程案例，pipeline 成熟。
- **要补**：
  - 建**规则知识库**：整理 `doc/references/` 已有的真实制度/规范/模板（电子公文系统管理办法、流程要素管理文档、模板）→ 切分入向量库。
  - 设计 agent **接入 RAG**：检索适用规则作为约束 + **证据引用**（改动/字段有据可依、可追溯）。
  - 评测加 **规则合规率** 维度（见 §4）。
- **停止线**：3 个锁定案例端到端跑通、产物干净、评测有分数即冻结。**不再加新流程类型**；source 摄取**不再加花活**（已过度）。

### M2 · 薄运行时（数据底座，薄做）

- **现状**：runtime engine（form_renderer / condition_eval / handler_resolver / store）+ slice1 API + SPA，基本能跑通、支持不同节点用户审批。
- **要做**：跑通 **1–2 个流程的 happy path**（发起→填写→审批→流转→结束），关键产出是**结构化事件日志**（见 §6）。
- **停止线**：一条 happy path 能演示 + 能产出事件日志即冻结。**坚决不做平台化功能**（见 §5）。

### M3 · 运营分析 Agent（护城河②，深做）

- **要做（两层，确定性与 LLM 分离）**：
  1. **确定性指标计算**（SQL/pandas，不用 LLM 算数）：平均处理时长、人工介入比例、环节停滞、最后环节停滞、退回率——**复用前司效能看板的指标定义**。
  2. **LLM 分析层**：在算好的指标之上识别堵点（阈值 + 推理）、归因、生成结构化优化建议。
- **text-to-sql**：核心用**预定义指标工具**（`get_node_dwell_times`、`get_return_rates`…，可靠）；text-to-sql 作为**可选"自由问答"加分层**，限定固定 schema 的 event 表，低风险，**别让它扛核心数字**。
- **停止线**：确定性指标 + 堵点阈值识别 + LLM 归因/建议 + 回灌设计；text-to-sql 一个 demo 问答点到为止。

### M4 · 闭环反馈（轻量，但这是 headline）

- **要做**：把 M3 的优化建议作为**设计输入**回灌 M1 重跑（哪怕半自动），展示"流程被分析→被改进"。
- **停止线**：能演示一次"建议→改进"的闭环即可。

## 4. 评测体系设计（项目的差异化重点）

核心原则：**区分"离线评测（有 gold）"和"生产评测（无 gold）"**，两套都要，且 demo 都展示。

### 4.1 离线评测（有 gold，做研发 benchmark）

- **逻辑**（已基本正确）：`gold_source → target.json（参照）`、`模拟 source → LangGraph → output.json（预测）`，两边归一成同一 schema 再比（标准的 normalize-then-compare）。把 **待确认项** 与 **错误项** 分开——源里本就没有的信息应触发澄清，不算抽错。
- **唯一弱点 & 修复**：现在 target 也是 AI 抽的 = 在测"AI vs AI 一致性"而非准确率。**修复：作为领域专家手工校正 target 成真 gold**，3–5 个案例人审定稿即够（gold 小而准 > 大而糙）。并**控制模拟 source 的信息含量**（哪些"在源里、考抽取"、哪些"故意省、考澄清"），让评测公平可解释。
- **怎么人审（不看 JSON）**：
  - **读**：把 target.json 渲染成 **Excel + drawio**（pipeline 本就产出），与原始真实流程文件**并排比**。这就是你做了多年的"流程要素管理文档"格式，看这个最快最准。
  - **改**：别手抠 JSON。把 target 做成**结构化表格**（sheet：FormFields / FlowNodes / Paths / Roles，对应 JSON 的几个 list）+ 一个**很小的 表格↔JSON 同步脚本**；在 Excel 里审改，脚本同步回 JSON。JSON 当存储，表格当编辑界面。
  - 偶尔小修直接改 JSON 也可接受（3–5 个案例不值得专门搭审阅 UI）。
- **评测产出**：跨案例汇总成**一张表**（案例 × 要素级准确率 / 总分 / 合规率），外加一张图。这是 demo/面试"证明它好用"的硬证据。

### 4.2 生产评测（无 gold，reference-free）

真实使用时面对全新流程、没有 gold，只能靠专业人员人工核对。设计如下：

1. **规则合规检查（RAG，天然 reference-free）**：输出有没有违反检索到的公司制度 / schema / 内部一致性——不需要 gold 也能打分（检索机制见 §9）。
2. **结构 / 完整 / 一致性校验**（已有）+ **缺失 / 冲突检测**：agent 主动标红不确定、冲突的要素。
3. **Human-in-the-loop = 评测信号**：流程 owner 审改，把**"人工修改量 / 采纳率"**当生产质量指标；**人改后的版本沉淀为新 gold**（数据飞轮，gold set 越用越大）。

> demo 里两套都展示：①离线 benchmark 表；②"生产模式"面板（规则合规分 + 待人工复核标红项 + owner 复核/修改 + 修改回流）。这体现"研发评测 ≠ 生产评测，且都设计了"的眼界。

### 4.3 分析 Agent 的评测（M3）

- **埋已知堵点**：合成数据时故意注入一个已知堵点（如某环节停留特别久），看分析 agent 能否检出 → 用"检出率"评测分析侧，分析侧也有了可量化指标。

## 5. 要砍掉 / 冻结的功能（过重，偏离主线）

> 原则：OA = 数据底座，不是产品。以下功能**直接挪走或冻结**，不再投入。

| 功能 | 处置 | 原因 |
|---|---|---|
| **完整组织架构平台**（组织树、人员管理、多层级） | **砍**，仅保留 demo 够用的**最小组织/角色映射**（解析处理人来源用） | 无底洞，非 AI 差异化 |
| **用户体系 / 用户隔离 / 登录鉴权** | **砍 / 冻结**（demo 用模拟用户即可） | OA 平台功能，与 AI 主线无关 |
| **草稿 / 已办 / 历史 全功能** | **冻结**（happy path 不需要） | 平台纵深，边际价值低 |
| **工作台（我的工作台）全量功能** | **冻结**，只留一条审批 happy path 所需视图 | 同上 |
| **Slice 1「目标产品从零重设计」** | **暂停**（PRD v0.6 的全量目标对求职时间线是陷阱） | 范围失控来源 |
| **更多流程案例**（>3 个锁定） | **冻结** | 边际收益递减 |
| **更多测试**（现 13 个测试文件已足够） | **冻结** | 已够用 |
| **source 摄取继续加花活**（修复/质量/parser 建议已过度） | **冻结** | 已过度工程化 |
| **SPA 继续扩展工作台/流程管理模块** | **冻结**，只维护 demo 必需视图 | 7221 行已够，别再长 |

> 说明：组织/角色不是全砍——**运行时解析处理人（本部门/本公司/特定部门/角色）需要一份最小的组织+角色映射**，保留这份最小数据即可，不要做成可管理的组织架构平台。

## 6. 数据策略（运行事件日志）

- **事件日志 schema**（process mining 风格的 event log）：
  `case_id（实例）· activity（节点）· resource（处理人）· enter_time · leave_time · duration · action（提交/退回/驳回）· outcome · is_manual_intervention`
- **来源两路，同一 schema**：
  1. **少量真跑**：薄运行时跑几条 happy path → 真实实例（验证全链路 + 证明"设计的流程真能流转"）。
  2. **大量合成**：**合成事件日志生成器**按流程定义采样路径 + 从可配置分布采样时长/处理人，**注入真实模式**（堵点/高退回/人工介入），批量造几百条。
- **不需要在系统里一条条真流转几百次**。少量真实证明闭环成立，合成数据提供统计丰富度（透明标注"运行数据为模拟"，标准且可辩护）。
- **加分**：用真实业务经验**校准分布**（典型处理时长、退回率、人工介入比例来自你看板经验），让模拟数据像真的；并**埋已知堵点**用于评测分析 agent（见 §4.3）。

## 7. 对话式修改 Agent 的 harness（M1 的交互层）

> 心法：它不是"自由聊天 agent"，是**在结构化对象（ProcessDefinition）上操作的 agent**——通用在交互，专用在工具。

需要的 harness 部件：

1. **结构化编辑工具**（核心）：增/改/删 字段、增/改 节点、改处理人、加路径/条件、改角色……每个 typed + Pydantic 校验。
2. **编辑后校验**：复用结构校验 + 业务校验 + **RAG 合规校验**；违规则警告/拦截。
3. **diff + 确认**：展示前后变化，owner 确认（human-in-the-loop）。
4. **版本 / undo**：可回退。
5. **澄清缺失**：把"待确认项"做成对话里解决。
6. **依据引用**：改动基于某规则/某来源时给出引用。
7. **范围守卫**：只编辑当前流程定义，不发散。

- **停止线**：**5–8 个编辑工具 + 编辑后校验 + diff/确认 + 澄清** + 一段漂亮 demo 对话（例："金额超 50 万加一个总部审批节点" → agent 调工具改节点 + 校验 + 出 diff + 引用规则）即冻结。
- 这块是**练 agent harness 的最佳落点**，面试可直接讲"我为结构化编辑搭了一套 harness"。

## 8. 流程版本管理与发布

> 它是 **设计 → 运行 的桥**，也是闭环的核心拼图：对话修改 agent（§7）和 M4 优化反哺都会让同一条流程产生多个版本，而"用运行数据证明改了之后变好"必须靠版本对比。所以要加——但只加**最小且正确**的一层，不做成完整生命周期平台。

### 8.1 为什么是核心（而非可砍的 OA 功能）
1. **版本对比 = 闭环 payoff**：v1 有堵点 → 分析给建议 → v2 落地 → 对比"X 环节平均时长 A→B、退回率 C→D"，正好复刻简历"办结时长↓27.9%"，是最强量化故事。
2. **运行正确性**：在跑的实例必须钉在它启动时的版本，否则定义一改、在途实例就乱。

### 8.2 最小且正确的设计
- **带版本的 ProcessDefinition**：`process_key`（稳定标识）+ `version`（v1/v2…）+ `status`（draft / published / deprecated）+ **lineage 血缘**（从源抽取 / 对话编辑自 vN-1 / 分析建议优化自 vN-1）。
- **发布 = 带质量门的不可变快照**：draft → publish → published（immutable）。**发布门**：通过 schema 校验 + 业务校验 + 规则合规(RAG) +（有 gold 的案例）评测分数阈值，才允许发布——**把评测体系嵌进发布门**（"不达标不上线"，既有产品意义又是强面试点）。
- **运行时实例化"已发布版本"**：新实例绑定当前 published 版本；**在途实例钉住自己的版本**（`definition_version`），不热迁移。
- **按版本分析 + 对比**：M3 指标按版本分别算，事件日志每条带 `definition_version`；合成数据**跨版本生成**（v1 带堵点、v2 修复后）以演示"优化生效"。

### 8.3 要砍的（保持轻）
- ❌ 发布审批流 / 多角色会签上线（publish = 一个动作 + 质量门即可）
- ❌ 在途实例**热迁移**到新版本
- ❌ 灰度 / AB / 金丝雀 / 复杂回滚编排（最多"停用 + 重新发布旧版"）
- ❌ 版本分支 / 合并；❌ 完整审计 / 权限体系
- ✅ 保留：线性版本（v1→v2→v3）、三态、发布质量门、版本钉、按版本分析对比

### 8.4 复用现有、别重建
在 `app/runtime/store.py` 和 `data/runtime/design_initializations/...` 持久化层上**扩**一个版本存储：`(process_key, version) → 不可变快照 + 元数据{status, created_at, lineage, publish 时 eval 分}`，不新造。

### 8.5 停止线
带版本的定义 + 带质量门的发布 + 版本钉 + **一组 v1 vs v2 效能对比**能演示，即冻结。不碰审批流 / 灰度 / 热迁移。

## 9. 规则 RAG 设计（M1 的知识层）

> 设计流程时，agent 需检索"公司级/系统级制度与规则"作为所有流程设计的**依据与约束**。这层既喂**生成**（约束 + 引用），又喂**评测**（合规率），形成子闭环。

### 9.1 现状（可用，方向对）
- `data/knowledge/` 已有 7 份带 frontmatter 的规则 md（`business_domains / applies_to_processes / rule_types / risk_boundaries`），`app/org_knowledge.py` 据此做**结构化筛选 + 校验**——不是裸向量 RAG。
- 对合规类规则，这个方向**正确**：宁可全、不可漏，强制规则不能交给相似度阈值。**保留为主干，不要换成裸向量 RAG**。

### 9.2 推荐：两阶段混合检索
1. **结构化筛选（主干 · 确定性）**：按 domain / process_key / 金额 / 印章类型 选出"候选规则集"，保证不漏（你已有的，继续用）。
2. **语义检索（补充）**：在候选集（或全库）内，用当前流程内容（字段/节点/金额/特殊事项）embedding 召回最相关的**规则条目/子句**，解决长文档 + 语义触发（如出现"客户承诺/对外合同"才适用的规则）。
3. **rerank + 引用**：排序后带 `rule_id` + 来源子句作为证据，给设计 agent 引用、给合规评测核对。

> 卖点（面试可讲）：合规场景用**结构化筛选保完整性 + 语义检索保精度**，不把强制规则命中交给相似度阈值。

### 9.3 接入 pipeline（双用）
- **设计时（生成约束）**：检索适用规则 → 影响结构（金额≥5万 → 加财务负责人审批；公章 → 先法务审核）+ agent **引用规则**。
- **评测时（合规检查）**：ProcessDefinition 对规则核验——**结构化规则走确定性检查**、定性规则走 **LLM-judge** → 合规率（与 §4.2 生产评测打通）。
- **对话修改时**同样复核 + 引用（§7）。

### 9.4 模拟文件重构（保留 frontmatter，改成"原子规则"）
- **从"按文档"改为"按规则条目（atomic rule）"**，每条 = `rule_id + 适用条件 + 要求 + 来源(provenance)`，例：
  ```yaml
  - rule_id: SEAL-003
    适用条件: 印章类型 ∈ {公章, 合同章}
    要求: 必须存在"法务审核"节点且早于"行政审批"
    可机检: true
    来源: 印章与合同管理办法 §X
  ```
  一次解决三件事：**精确检索 + 子句级引用 + 可机检的合规评测**。
- **制度规则 vs 要素规范/模板分开**：制度 → 进 RAG 语料；要素规范/模板（合法要素文档的结构）→ 归 schema / structural 校验，别混进检索库。
- **provenance（来源标注）**：每条标"仿自哪份真实文件/章节"，可辩护可追溯——**只有少量真实文件完全 OK，小而真 + 结构化 >> 大而糊**。
- **聚焦 3 个锁定案例**：只覆盖 印章 / 邀约 / 报销(或采购) 的规则，~20–40 条足够。

### 9.5 停止线
原子规则集（覆盖 3 案例）+ 两阶段检索（结构化 + 语义）+ 引用 + 用规则做合规评测，能演示即冻结。**不做**：全公司规则库、规则管理 UI、灌入全部真实文档。

## 10. 贯穿全局的设计原则

**确定性的归确定性，LLM 的归 LLM。**

- 评测 = 确定性打分（对 gold）+ 无参照检查（规则 / judge）。
- 编辑 = typed 工具 + 校验（确定性）+ LLM 解析意图。
- 分析 = 确定性算指标 + LLM 归因 / 建议。

把这条原则讲出来，本身就是很强的资深产品 + 工程判断。
