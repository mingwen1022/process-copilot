# 流程设计 Agent —— 产品功能全景

> AI 流程全生命周期闭环：**设计流程 → 上线流转 → 运行数据分析 → 优化反哺设计**，
> 再加两条纵向：**对接真实 OA 引擎（飞书）** 证明可移植性，**流程参与者 AI 副驾** 覆盖运行期人机交互。
> 本文按功能模块盘点：每个模块的「设计 / 现有（含节点逻辑与 prompt 设计）/ 要做」。设计侧、分析侧、副驾侧三处 AI 深做，运行时只作产生运行数据的薄底座（并抽象为可插拔的实例接口）。

## 全景图

```
        ┌──────────── 规则知识库 (RAG) ────────────┐   ← 设计/分析/副驾 三处都从这检索依据
        │ 制度 · 流程要素规范 · 运维处理规则 · 模板  │
        └───────────────┬───────────────────────────┘
                        │ 检索"适用规则"作为设计约束与依据（并用于合规评测）
   多源需求 ──▶ ① 设计 Agent ──▶ 标准流程定义(JSON) ──▶ ⑨ 翻译器 ──▶ 飞书审批(真实 OA 引擎)
                        │              │ 评测：要素级准确率(对 gold) + 规则合规率(无参照)
        对话式修改 ⟲────┘              ▼
                            ② 薄运行时(happy path) ──▶ 结构化运行事件日志
                                     │   (抽象为可插拔"实例接口"；+ 合成事件日志生成器)
                                     ├──────────────▶ ⑩ 参与者副驾（发起前/卡住时/办理中）
                                     ▼                    诊断·override授权·材料合规体检
                            ③ 运营分析 Agent ──▶ 效能指标 + 堵点 + 优化建议
                                     │
                                     └────▶ ④ 优化建议反哺 ① 重新设计  ⟲ 闭环
```

**贯穿原则——确定性的归确定性、LLM 的归 LLM**（全项目一以贯之）：评测=确定性打分+无参照检查；编辑=typed 工具+校验+LLM 解析意图；分析=确定性算指标+LLM 归因/建议；**副驾=LLM 判断/解释，诊断·动作构造·校验·应用全是确定性代码**；飞书翻译=纯确定性映射。设计 pipeline 里只有"抽取"和"业务校验"两个节点用 LLM，其余全是确定性代码。**LLM 只在"理解意图/组织语言"处出现，能判对错的事绝不交给它猜。**

# 1. LangGraph 设计 pipeline + 多源摄取

**职责**：把多份零散、多格式的真实业务材料，整合成一份标准流程定义（`ProcessDefinition` JSON），并对 gold 评测。**设计 agent 的核心产出只有标准定义 JSON**（人可读的其它格式属衍生视图，不在主功能范围）。

## 1.0 图结构与路由

```
source_file_loader ──▶ source_context_builder ──▶（route）
                                                  ├─ 上下文过大 ─▶ workflow_design_output_writer（跳过抽取）
                                                  └─ 正常 ─▶ process_extraction_agent ──▶ structural_validator ──▶（route）
                                                                                            ├─ schema 失败且有重试额度 ─▶ retry: process_extraction_agent
                                                                                            ├─ schema 通过 ─▶ business_validation_agent ──▶（route）
                                                                                            │                                              ├─ 需修复且有额度 ─▶ retry: process_extraction_agent
                                                                                            │                                              └─ ─▶ workflow_design_output_writer
                                                                                            └─ schema 失败无额度 ─▶ workflow_design_output_writer
```

- 用 `StateGraph(WorkflowState)` 编排，节点产物按目录分类写盘：`logs/<node>/`、`eval/`、`product/`。
- 路由是**确定性函数**：`route_after_structural_validation`（retry_extraction / business_validation / write_outputs）、`route_after_business_validation`（retry_extraction / write_outputs）。重试有上限（`max_validation_retries`，默认 1），避免死循环。

## 1.1 `source_file_loader`（确定性）

- 从 case 目录（`raw_sources/` 或上传 manifest）发现 source 文件，逐个调 `parse_source_file` 解析。
- **多格式解析**（`app/tools/source_parsers.py`）：docx / doc(识别为 html) / xlsx / csv / md / txt / png / pdf。
- **图片视觉转录**（`app/tools/vision_ocr.py`）：图片 source（聊天记录/系统截图/表格截图等）由多模态 Claude **忠实转录**为文本进入上下文——只转录、保结构（发言人/时间/字段-值/行列）、不推断，理解留给下游 agent。默认开启（CLI `--no-vision` 可关、测试中默认关不联网）；转录失败降级为 warning、不阻断。"仅参考"类线下件即使被转录，仍受下游"线下参考不照搬为节点"护栏约束。
- **二进制护栏**：扫描版 pdf（无文字层）暂仍触发 `requires_ocr` warning（PDF 光栅化+视觉为后续增量）；解析出的 chunk 若含二进制特征则过滤，不把乱码写入上下文。
- 产出：`source_file_manifest`、`source_chunks`（带 chunk_id / source_file / source_type）、`ingestion_warnings`、`source_package_ref`，全部落 `logs/source_ingestion/`。

## 1.2 `source_context_builder`（确定性）

- 把 chunks 整理成 **source 目录（catalog）** + **source 上下文（context）**，建 `source_index`，挑选 seed chunks。
- **上下文预算**：超过 `MAX_SOURCE_CONTEXT_CHARS` 时记 `context_error=context_too_large`，路由**直接跳到输出节点**（不调 LLM，避免超长上下文）。
- 产出：`source_context.txt`、`source_catalog_context.txt`、`selected_seed_chunks.json`、`context_budget_report.json`。

## 1.3 `process_extraction_agent`（**LLM 节点**）

**节点逻辑**
- 用 `with_structured_output(ProcessDefinition, method="function_calling", include_raw=True)` 让模型按 schema 产出 `ProcessDefinition`。
- **JSON 自修复**：若 structured output 解析失败（`parsing_error`），用一段"JSON 格式修复器"prompt 再调一次，把坏 JSON 修好；各 attempt 的 `llm_raw_output_attempt_N.txt` / `llm_raw_output_final_attempt_N.txt` / `messages_attempt_N.json` 落盘。
- 重试时（来自 validator 回边）把 `validation_feedback` 拼进 user prompt，并强调"只按 source 修，不要因 validator 提示而编造"。

**Prompt 设计**（system prompt，去案例硬编码后的现状）
- **通用要求（8 条）**：输出符合 schema；早期 vs 后续冲突取后续拍板；V1 只保留简化字段范围；只产出流程定义 JSON、不生成衍生视图或报告；不发起补问（缺失交给 business validation）；线下实例材料只作参考、不机械照搬纸质转办/线下备案为线上节点；线下操作优先判断是否映射为字段/通知/附件；文本不嵌英文双引号。
- **字段命名与规范化规则（7 条，通用）**：① **字段名忠实使用 source 原文短名，不带流程名前缀、不自行同义改写**（例：source 写"联系电话"就输出"联系电话"，不要改成"紧急联系方式"；"工作交接人"不要改成"代理人"）；② 仅当 source 提到标题时才输出"标题"字段；③ 自动带出/只读字段→只读文本 + required=[]；④ 起草填写字段 required=["draft"]；⑤ 自动计算字段 required=[]、editable=[]；⑥ 不编造处理时限；⑦ 不编造附件/角色。
- **审批环节与路径规范化规则（6 条，通用系统约定）**：① 起草节点固定 `node_id="draft"`；② **node_id 用英文蛇形、node_name/handler.role 忠实使用 source 原文称呼，不自行改写**；③ 意见条件统一"结论性意见=同意/不同意"；④ 退回起草统一 `target_node_id="DRAFT"`；⑤ 流程结束统一 `target_node_id="END"`；⑥ **只依据 source 实际描述输出，不套用任何固定流程模板或预设节点清单**。
- **冲突处理规则（3 条）**：早晚口径冲突取后续；后续标"待确认"但前文已有明确口径则草稿先采用明确值、不输出 `<UNKNOWN>`；这类待复核项保留确定值、由 business validation 生成待确认项。
- **注入 conventions 系统词表**（见 1.7）+ **注入 ProcessDefinition JSON Schema**。

> ⚠️ 关键设计决策：此 prompt 曾焊死"员工请假申请字段模板"、字段名映射、案例节点映射（dept_supervisor/dept_gm 等）——既把 gold 答案泄漏给 agent，又劫持同类新流程。已全部剥离为上面的**通用规则**，并加回归测试保证不复发。

## 1.4 `structural_validator`（确定性）

- 对候选 `ProcessDefinition` 做三层确定性校验：
  1. **Pydantic schema 校验**（候选为空则尝试从 `llm_raw_output` 解析）。
  2. **引用完整性**（`_validate_process_references`）：submit_paths 的 `target_node_id` 必须指向已存在节点或保留别名 `DRAFT`/`END`。
  3. **conventions drift 警告**（`validate_process_conventions`，**非阻断**）：组件 options 缺失、案例级口径偏差等出 warning。
- 写 `schema_validation_report.json`（valid / schema_errors / convention_warning_count），决定路由（通过→业务校验；失败→重试或直接输出）。

## 1.5 `business_validation_agent`（**LLM 节点**）

**节点逻辑**
- 审核候选是否忠实 source，产出 `BusinessValidationResult`：`passed` / `blocking_issues` / `warning_issues` / `raw_missing_items` / `user_clarification_requests` / `repair_instructions` / `summary`。
- 有 blocking 且有重试额度 → 触发 `retry_extraction` 回边修复；否则进输出节点（缺失/待确认进报告与设计页）。

**Prompt 设计**（system prompt，去案例硬编码后的现状）
- **边界（5 条）**：不使用 gold；不重新生成完整 JSON，只审核+给修复建议；必须基于 source 举证、不靠常识猜测；blocking 仅用于明显不可用；人审边界只用于判断哪些能力暂不进 demo、不反推标准答案。
- **重点检查（4 条）**：大块缺失（字段/环节/路径/角色/附件）；source 明确提到却遗漏的关键要素；无依据的编造；条件/角色/可见可编辑与 source 明显冲突。
- **证据状态（3 档）**：`found_in_raw`（有依据→退回 extraction 修）/ `not_found_in_raw`（无依据→进缺失报告、不编造）/ `uncertain`（谨慎，仅阻断质量时 blocking）。
- **blocking 克制**：冲突但已有可运行口径→warning + 待确认项，不 blocking；时限/附件/字段长度/手机号格式等发布前优化项→warning。
- **注入 conventions 系统词表**（同 1.7）。
- **V1 系统约定与运行时能力边界（通用，不误判为问题）**：draft/DRAFT 别名是约定；**字段名/节点名/角色名忠实 source 原文、不因没改写成"标准"同义词而 warning**；运行时不支持同环节多人并行/会签（"结束本人处理"等不作 blocking）；运行时不支持并行分支（"同时送"等作 warning/待确认）；人审边界内的线下/并行动作不作 repair blocking。
- **用户确认项规则**：source 没写/冲突/需业务口径→写 `user_clarification_requests`；出现"待确认/暂未配置/上线前确认/是否允许"必须生成确认项；每项问题式表达 + 2-3 个**互斥不重复**的业务口径选项（不放"手动输入/按建议处理"泛化项）；能从 source 明确修复的写 `repair_instructions` 而非确认项。
- **JSON 硬约束**：符合 `BusinessValidationResult` schema；字符串简短、不摘原文长句、不用英文双引号；`source_hint` 只写文件名+chunk id。

> ⚠️ 同样已剥离案例硬编码（"请假天数＞3"、按自然日、"一级主/辅负责人"、dept_gm 映射等），改写为上面的通用运行时能力边界声明。

## 1.6 `workflow_design_output_writer`（确定性）

- 组装并落盘三类产物：
  - `product/`：`process_definition.json`、`workflow_design_output.json`（含 `status`：draft_ready / blocked_missing_source / failed_schema_validation / context_too_large）、`designer_assistant_message.json`（设计助手消息 + 澄清卡片）、`user_clarification_requests.json`、`validation_summary.json`。
  - `eval/`：`gold_target_snapshot.json`（gold 是 human_reviewed 时）、`actual_eval_target.json`。
  - `logs/legacy_eval/`：与 gold 的对比报告 + 缺失报告（开发期参考）。
- **澄清卡片**做去重（同一确认项的重复选项合并）、生成推荐项，供设计页/对话交互使用。

## 1.7 conventions 系统词表（两个 agent 共享的"规则注入"）

`render_conventions_for_prompt()` 注入到抽取与业务校验两个 prompt，是**唯一的通用系统规则源**（与具体流程无关）：
- **组件类型词表**：`component_type` 只能取 schema 的 `ComponentType` 全枚举（单行文本/多行文本/下拉单选/下拉多选/单选按钮/日期/数字/员工选择/部门选择/只读文本/文号/…）；业务枚举优先下拉、选项必须写入 `options`。
- **处理人配置词表**：`handler.source` 只能取 `HandlerSource` 枚举（本部门/本公司/本条线/特定部门/表单字段指定/不指定）、`handler.mode` 取 `HandlerMode` 枚举；`source=表单字段指定` 时必须给 `source_field`。
- **必填环节口径** + **路径条件口径**（固定短语"结论性意见=同意/不同意"、"最后一人/部门最后一人/多环节最后一人"的语义释义、当前 demo 不支持的并行/会签动作）。
- 配置在 `data/config/process_design_conventions.json`；其中**案例级规则**（`case_rules`）**不进 prompt**，只由 `validate_process_conventions` 做事后 drift 校验（生成不知道答案、校验才知道）。

**现有汇总**：6 节点 pipeline、多格式解析、**图片视觉转录**、JSON 自修复、2 个核心 agent（抽取/业务校验）、schema、conventions 单一源、2 个案例（EOA140 + 请假，含真实群聊截图 source）。
**要做**：扫描 PDF 的视觉转录（需光栅化）；源摄取已偏过度（~16 产出文件）维持冻结；prompt 保持通用无硬编码（已有回归保护）。

# 2. 评测体系

**设计**：对人审 gold（`target.json`）三维加权打分（满分 100）；区分「离线评测（有 gold，研发 benchmark）」与「生产评测（无 gold，靠规则合规 + 人审）」。

**三维与打分公式**（`app/eval/process_target_eval.py`）
- **确定性流程要素（70）** = meta5 + form_fields20 + flow_nodes15 + submit_paths15 + attachments8 + roles7。每个 list section：`score = weight × (0.60·recall + 0.30·attribute_accuracy + 0.10·precision)`；recall=命中 gold 条目比、precision=非幻觉比、attribute_accuracy=已匹配条目里属性对得上的比（submit_paths 每条条件不一致即整条算错，最敏感）。
- **待确认项（20）** = `0.60·required_recall + 0.25·quality_ratio + 0.15·forbidden_clean`：该问的有没有问到（命中 `clarification_targets`）+ 问得有没有质量（≥2 项{问题/推荐/选项/证据}）+ 不该问的有没有乱问（`forbidden_clarifications`）。
- **证据+护栏（10）** = `0.50·evidence_ratio + 0.50·guardrail_ratio`：`evidence_map` 引用的源文件是否在摄取清单中 + 是否命中禁止澄清/噪音。
- **安全阀**：hard_failures（无起草节点/无 END/schema 错→直接 fail）；caps 封顶（gold 有附件但没抽→封 80；必答澄清全漏→封 80；命中禁止澄清→封 85）。状态：≥90 pass / ≥80 needs_review / 否则 fail。

**gold 结构**（`deterministic_process_definition` + `clarification_targets` + `forbidden_clarifications` + `guardrail_targets` + `evidence_map` + `eval_weights` + `review_metadata`）。

**现有**：`process_target_eval` + `eval_schema` + `comparison` + `export_target_review` + `batch_eval`；CLI + 机读 json + 人读 md scorecard；review 门禁（正式评测要求 human_reviewed/locked）；人审回路（auto vs human_adjusted 数据飞轮）；一键跨案例汇总 `scripts/run_eval_summary.py` → `doc/eval_summary.md`：**EOA140 94.75 / 请假 90.74**。

**要做**：散文型字段（`logic_description`）与结构化属性分开评分（避免逐字严比偏苛）；form_fields 字段名模糊对齐；生产评测合规率接 RAG；请假 gold 人审定稿（draft→human_reviewed）。

# 3. 规则 RAG（知识层）

**设计**：跨流程的公司/系统级制度规范知识库，设计时检索"适用规则"作约束 + 引用，评测时做合规检查；两阶段混合检索——**结构化筛选保完整性 + 语义召回保精度**，强制规则不交给相似度阈值。

**已实现**（模块 3 · Phase 0–6 全部跑通，设计/分析两端运行时都从这里检索依据）

- **语料重建**（`data/knowledge/`）：多维度带 frontmatter 语料——policies（请假/子公司重大事项/授权矩阵/电子公文/印章合同/费用报销）、design_standards（流程要素设计规范）、org_roles、process_playbooks、ops_baselines；frontmatter 标注 `doc_id/dimension/applies_to_processes/applies_to_domains/synthetic:true`，全部为合成语料（真实制度文档仅作形态参照，不入库）。
- **原子规则**（`data/schema/rule_schema.py` + `data/knowledge/rules/*.json`）：15 条 `AtomicRule`（`rule_id` + `applicability_condition` + `requirement`{`CheckKind`} + `provenance`{源文档+子句} + severity），12 条确定性可校验 + 3 条 LLM-judge。原子规则 ≠ 文本块：前者是代码能逐条 CHECK 的结构化对象，后者是供语义召回的文本，二者共存于索引。
- **混合检索**（`app/rag/`）：Bedrock Titan Text Embeddings v2（1024 维）+ Chroma 持久化向量库；**结构化预筛（按 domain/process_id，确定性、不漏）∪ 语义召回（向量、模糊）**，结构化为主。带相关性阈值（默认 `max_distance=1.0`）——全部超阈值则**诚实返回空**，prompt 明确"无依据不编造引用"。
- **合规校验**（`app/rag/compliance.py`）：6 个确定性校验器按 `CheckKind` 分派逐条比对 ProcessDefinition；live 草稿拿到的是生成 id（AI-xxx），故用 `infer_domains` 关键词推断 + design_standard 规则恒生效来选适用规则。已接入设计 agent（引用规则子句作合规校验）。
- **有据归因**（`app/agents/process_analysis_agent.py`）：分析 agent 每个堵点候选检索知识、按来源去重、注入 prompt，诊断结论有据引用；无相关知识时不编造制度/基准引用。
- **评测**（`app/eval/compliance_eval.py` + `retrieval_eval.py`）：规则合规率（注入 6 个违规变体，recall 100%、0 误报）+ 检索命中率（10 条标注 query，recall@5 100% 全 rank-1）。
- **页面门面**（`制度与规则库`）：浏览原子规则库（按维度分组 + 确定性/AI 研判标签 + 出处）+ 语义检索 demo（真实向量库 + 相关性阈值 + 命中出处/距离），供演示"运行时 agent 走的同一条检索路径"。

# 4. AI 对话式修改 agent

**设计**：不是自由聊天，而是**在结构化对象（ProcessDefinition）上操作的 agent**——通用在交互、专用在工具。LLM 只做"理解指令 + 决定改不改、改哪里"，怎么改（apply）、改完是否合法（校验）、改了什么（diff）全部是确定性代码。

**现有**（已实现，非雏形）
- **编辑内核**（`app/tools/process_edit_tools.py`）：16 个 typed 编辑操作，覆盖 6 类对象（表单字段/流程环节/提交路径/附件/角色 各 add-update-remove + update_meta）的判别联合；`apply_edit_operations` 确定性应用，找不到引用报错不臆造；显式 `clear_*` 标记区分"不改"与"清空"，避免同值更新被误判为变更。
- **对话式修改 agent**（`app/agents/design_edit_agent.py`）：单轮指令 → `EditProposal`（reply + operations + resolved_clarification_ids + **out_of_scope 范围守卫**）；模糊指令反问而非瞎改，超范围指令拒绝且清空 operations。
- **diff 引擎**（`app/reporting/process_diff.py`）：编辑前后 ProcessDefinition 对称对比（区别于 `comparison.py` 的 gold-vs-actual 语义），结构化产出 added/removed/changed（含节点下嵌套的提交路径变更）。
- **会话服务接入**（`workflow_design_service.generate_draft`）：取最新未处理的用户消息 → agent 解析 → apply → 校验 → diff → 落库为新草稿 + 一条 assistant 消息；`last_processed_message_id` 防重复应用同一条指令；`source_context` 把用户上传的补充材料喂给 agent（覆盖"补充信息"场景）；`open_clarifications` 优先取 LangGraph 初始化产出的结构化待确认项（真实 id）。
- **单步 undo**：`previous_draft_definition_json` 保存编辑前草稿，仅在 **diff 判定真实发生变更**时才更新（问答/重复确认/同值更新等无实际数据变化的回合不会覆盖可撤销状态）；`session.can_undo` 供前端判断。
- **设计页 UI**：聊天消息按 event 类型渲染——reply 气泡 + 结构化 diff 卡片 + 错误提示条 + 撤销按钮，不与初始化消息的 assistant_message/clarification_cards 回退逻辑混用。
- 真实 Bedrock 端到端验证：复杂多操作指令正确分解（如"超过 X 天再加一级审批"→新增节点+改路径条件+加新路径）、超范围指令正确拒绝、模糊指令正确反问、undo 正确恢复。

**执行链路详解（举例：用户说"把请假事由改成必填"）**

```
用户发消息 ──▶ add_message（纯存储）──▶ generate_draft（唯一入口）
                                            │
                                  latest_user_message.id == last_processed_message_id ?
                                     ├─ 是 ─▶ 直接返回，不调用 LLM（防重复应用同一条指令）
                                     └─ 否 ─▶ 继续
                                            │
                          组装上下文：process JSON + 对话历史 + 待确认项 + 上传材料(source_context)
                                            │
                              DesignEditAgent.run()（唯一有 LLM 的一步）
                                            │
                                  ① 拼 system+user prompt（含当前流程定义全量 JSON）
                                  ② structured_model.invoke()（一次 Bedrock 工具调用/function calling）
                                  ③ 模型一次性返回 EditProposal：
                                     reply + operations（每个 op 里含判别符 op 字段和 updates 子对象）
                                     + resolved_clarification_ids + out_of_scope
                                     （out_of_scope=true 时代码强制清空 operations，双保险）
                                            │
                            apply_edit_operations(process, operations)（确定性，非 LLM）
                                  ├─ 深拷贝 process，找不到引用的字段/节点/路径就报错、不臆造
                                  ├─ 逐个 op 分发（如 update_form_field）
                                  └─ 值和当前相同则跳过、不计入"已变更"（避免同值更新被误判）
                                            │
                          diff_process_definitions(旧草稿, 新草稿)（确定性，纯对比）
                                            │
                             has_real_changes = diff["has_changes"]  ← 唯一可信依据
                          （不用 apply_result.applied：它只代表"操作没报错"，
                            不代表"数据真的变了"——同值更新也会被记入 applied）
                                            │
                        校验新草稿（结构+业务规则）──▶ 落库：
                          draft_definition_json = 新草稿
                          previous_draft_definition_json = has_real_changes ? 旧草稿 : 保持不变
                          last_processed_message_id = 这条用户消息 id
                          追加 assistant 消息：content=reply（纯文本）
                                              payload={diff, errors, event, resolved_clarification_ids, ...}
                                            │
                        session_payload() 返回整个会话 ──▶ SPA 渲染
                          reply 气泡 + 结构化 diff 卡片 + 错误提示条
                          + 撤销按钮（仅当 isLast && session.can_undo）
```

这条链路里，**LLM 只参与"组装上下文→调用模型→拿到 EditProposal"这一段**；`operations` 里的 `updates` 子对象（如 `FormFieldUpdate{required_stages:["draft"], ...}`）是模型在**同一次**工具调用里跟 `reply`/`operations` 一起产出的，不是分步骤生成、也不需要再调一次模型解析。之后 apply / diff / 校验 / 落库 / 渲染全部是普通确定性代码，可复现、可单测。

真实例子的产出（同一次调用一次性返回）：
```json
{
  "reply": "「请假事由」字段已设置为起草环节必填。（该字段原本已在起草环节可编辑，本次仅将其标记为必填。）",
  "operations": [
    {"op": "update_form_field", "field_name": "请假事由",
     "updates": {"required_stages": ["draft"], "visible_stages": null, "max_length": null, "...": null}}
  ],
  "resolved_clarification_ids": [],
  "out_of_scope": false
}
```

**要做**：编辑后校验接入 RAG 合规检查（RAG 建成后）；依据引用（改动引用规则/来源，同样依赖 RAG）；多步 undo/版本历史（并入模块 6 版本管理时一起做，当前是单步简化）。

# 8. 闭环反馈

**设计**：把模块 7 的优化建议作为设计输入回灌模块 1 重跑，展示"流程被分析→被改进"；用 v1/v2 效能对比量化"优化生效"——整个产品的 headline。

**现有**（Phase 5 已跑通，headline，真实 agent-to-agent）：

**闭环是两个 agent 通过结构化诊断报告对话**，人不做翻译（`app/agents/design_feedback.py` + `scripts/run_design_feedback.py`）：
1. 分析 agent 诊断出每个堵点的自然语言修改建议（`suggested_process_edit_instruction`）。
2. 设计 agent（M4 `DesignEditAgent`）逐条把建议**自己翻成 typed 编辑操作**并 `apply_edit_operations` → v2 草稿。**翻译是 agent 的活，不是人肉手写**。
3. human-in-the-loop 只做判断：采纳哪几条、对含糊建议给**业务决策**（如升级门槛=14天，仍由 agent 翻成编辑）。

**真实回灌暴露的诚实事实**（比"全部完美映射"更有说服力）：设计 agent 有判断力——把"自动催办/自动拦截/异常监控"这类建议正确判为 `out_of_scope`（是**运行时/引擎能力**，流程定义表达不了）；对"短假豁免高层审批"这类含糊建议触发澄清守卫反问门槛几天；只有真正的定义级改动（路由条件、时限、表单校验字段）才落成编辑。即"很多运营改进本就不是流程定义的修改，而是引擎能力"。LLM 有非确定性，回灌跑一次冻结为 artifact（`process_v2.json` + `feedback_log_v2.json` 记录每条建议的真实归宿）。

v2 数据（`gen_leave_process_v2.py`）= 读 agent 产出的 v2 定义 + **建模改进**（削弱对应注入病灶，代表 SLA/表单校验等的预期效果，幅度是假设、每项对应一条采纳建议，数据侧的建模层）。控变量同到达/case-mix/种子（路由改动使两版非逐案例配对→同分布聚合对比，给出两版 case-mix 证明可比）。`version_comparison.py` 算 delta，效能分析页「版本对比」tab 展示。

**请假 v1→v2 结果**：平均办结时长 **76h→23h（↓70%）**、返工率 42%→16%、违规跳级 7→0、条线分管领导审批 116.6h→17.6h（↓85%）/SLA 28%→99%、到达该环节比例 28%→14%（升级门槛的**机械成立**效果，非调参）。诚实标注未改善项（部门主管处理时长 +4% 噪音）。**定性**：这是 what-if 流程仿真——机器/管线是真的、结构性改进机械成立；改进幅度是建模假设，不当作已验证 ROI。

**要做**：真正的 v1↔v2 版本管理与血缘（并入模块 6）；回灌目前脚本化，可做成设计页里"采纳建议一键生成 v2 草稿"的 UI（human-in-the-loop 勾选）。

# 9. 飞书对接（真实 OA 引擎）

**定位**：不是主战场，是**可移植性证明点**——证明"同一个设计大脑能把流程落地到一个完全独立的真实引擎并跑起来"，说明这套模式不锁死在单一运行时。诚实前提：现有 canonical `ProcessDefinition` 是从作者前公司引擎逆向出来的（并非天生中立），飞书是"引擎B"，两者各有独有能力（Venn，非超集）。当前架构（canonical + 翻译）本身就是"飞书=次要"的逻辑结果。

**现有**（端到端真发到真实飞书租户已跑通）：
- **确定性翻译器**（`app/integrations/feishu/translator.py`）：`ProcessDefinition → 飞书审批 create-definition 请求体`。翻译是确定性代码不是 LLM（两边都是结构化）。表单控件映射 + 节点线性化（飞书原生审批 API 只支持线性，条件分支被拉直并记 note）+ handler mode→节点类型 + 审批人默认逐级主管。有损映射全部收进 `notes`。
- **薄客户端**（`client.py`，标准库直连不引 SDK）：换 `tenant_access_token` → 创建审批定义 → 读回定义。`scripts/feishu_push_approval.py` 一键发。
- **表单控件保真**：飞书控件子格式文档查不到，**写探针对着真机逐个试出准确格式**（date/amount 需 `value:""`、contact 需 `value:{}`、number/部门/附件裸结构即可）；单选 radioV2 的 create 格式存在**读写不对称**（读回的格式喂回创建仍被拒），试约 20 种后止损、降级为文本并记录——这段"知道何时止损"本身是工程叙事。

# 10. 流程参与者 AI 副驾（护城河③）

**定位**：真实业务里流程上线后大量成本在**参与者与流程的交互摩擦**，通用产品很少做深。给流程生命周期三个触点各配一个 AI 副驾。都建在一层**抽象实例接口（端口-适配器）**上——只依赖 `InstanceContext`/`InstanceAction`，不碰冻结的 OA 运行时，Mock/OA/飞书可插拔。当前用 Mock adapter 驱动（`app/copilots/`）。

**贯穿纪律照旧**：LLM 只判断/解释，诊断·动作构造·校验·应用全是确定性代码，规则未覆盖升级人工，非法动作即便被授权也被 apply 层拦下。

**现有**（三副驾 headless + UI + 真机 LLM 验证已跑通）：

- **#4 发起问答**（发起前，纯只读）：推荐该走哪个流程（LLM 从目录选）+ **确定性路径预演**（`condition_eval` 拿用户假设属性沿 submit_paths 走一遍，"8天病假会经过 起草→主管→总经理→条线领导"，扎在真实定义、非 LLM 编）+ 资格/材料有据回答（规则 RAG，无据不编）。`app/copilots/launch_*`。
- **#3 运维**（卡住时）：三类根因确定性诊断（设计缺口=无路径 / 组织缺口=`resolve_role` 空 / 数据填错=值错）→ **分级路由**：数据订正=发起人确认；override(跳转/跳过/改派)=**生成授权工单转流程负责人 approve/reject**（不是空壳"已升级"）；规则明令禁止=`deny` 终局；无规则=`escalate` 升级。override 规则从**规则 RAG 检索**（与模块3 打通）。`app/copilots/ops_*` + 前端「运维授权台」。
- **#2 在办**（办理中）：打开在办任务**主动体检**（不是通用问答）——材料缺失（`condition_eval` 对附件 required_condition 求值）+ 合规红线（复用模块3 合规引擎跑流程定义）。`app/copilots/task_inspection.py` + 详情页「在办体检」面板。

真机验证：请假6天(填错)→改数据、5天(值对)→override转授权、授权台批准后实例真跳环节；病假10天在办→体检查出就诊证明缺失。三副驾共 30+ 测试。

**要做**：override 前的合规硬环节二次校验（复用合规引擎，防授权也不能跳合规硬环节）；`extensions` 扩展位承接引擎独有能力（YAGNI，有需求再加）。设计文档：`doc/流程参与者副驾-设计.md`。
