# 反哺闭环（运行洞察层）· 功能定义与设计

> 定位：把"设计 → 流转 → 分析 → **反哺设计**"这个环的最后一环补上。分析/运维在运行侧发现的问题，
> 结构化沉淀为「流程洞察」，在设计者下次编辑该流程时主动回流到设计 agent，形成可度量的闭环。
> 这是把四个模块从"并排的 demo"焊成"一个环"的连接组织。

## 0. 一句话定义

**一个按 `(流程, 环节, 问题类型)` 聚合的「流程洞察」存储**：运行侧（分析瓶颈、运维反复撞的设计缺口）
确定性地写入，设计侧在打开该流程时确定性地读出并回流给设计 agent；修订上线后确定性复检，洞察自动消解。

**为什么现在能做**：两端都已建好，只缺中间层——
- 分析侧 `detect_candidates()` → `CandidateBottleneck(node_id, severity[high/medium 确定性], metric_reference)`，
  `process_analysis_agent` → `DiagnosisReport / DiagnosisItem`。
- 运维侧 `ops_service.diagnose()` → `stuck_kind=design_gap`（覆盖漏洞：`blocked_paths()` 无前进路径）。
- 设计侧 `create_or_open_session(workflow_definition_id)` + `design_edit_agent`（对话式改）+ `business_validation`
  的 `UserClarificationRequest`（"发现问题→用户确认"的既有承接面）。

## 1. 确定性纪律（全项目一致）

| 环节 | 确定性代码 | LLM |
|---|---|---|
| 检测：是不是问题 / 多严重 / 哪个环节 / 命中几次 | ✓ thresholds、condition_eval、计数 | — |
| 归属 / 去重聚合 / 生命周期迁移（open→resolved） | ✓ | — |
| headline 人话、suggested_fix 措辞 | —（可先用模板兜底） | ✓ 仅组织语言 |
| 设计者据洞察改流程 | 校验由 structural / business validator 兜 | ✓ design_edit_agent 提议，**人确认** |

洞察是**确定性检测生成、确定性复检消解**；LLM 只负责"把数字说成人话"和"帮你改"，判对错的事绝不交给它。

## 2. 数据模型：`ProcessInsight`

```python
class InsightKind(str, Enum):
    COVERAGE_GAP = "coverage_gap"   # 覆盖漏洞：区间无路径（运维 design_gap）
    SLOW_NODE    = "slow_node"      # 环节停留过久（分析）
    HIGH_RETURN  = "high_return"    # 退回率过高（分析）
    SLA_BREACH   = "sla_breach"     # 超时达成率低（分析）
    ORG_GAP      = "org_gap"        # 岗位空缺无人可派（运维）
    # 与 CandidateBottleneck 的 detectors + ops stuck_kind 对齐，一一映射

class InsightSource(str, Enum):
    ANALYTICS = "analytics"
    OPS       = "ops"

class InsightStatus(str, Enum):
    OPEN         = "open"          # 新发现 / 仍存在
    ACKNOWLEDGED = "acknowledged"  # 设计者已看到 / 已进入修订
    RESOLVED     = "resolved"      # 修订后确定性复检已消解

class ProcessInsight(BaseModel):
    insight_id: str
    workflow_definition_id: str        # 归属哪个流程（与设计 session 同一把 key）
    node_id: str | None                # 归属哪个环节；None=流程级
    kind: InsightKind
    severity: str                      # high / medium —— 确定性，复用 CandidateBottleneck
    source: InsightSource
    evidence: dict[str, Any]           # 确定性支撑数字：analytics=metric_reference；ops=卡住单据明细
    occurrences: int                   # 命中次数：ops=卡住单数；analytics=样本量
    window: str                        # 统计窗口，如"近 30 天"
    headline: str                      # 一句话人话（LLM 或模板）
    suggested_fix: str | None          # 建议措辞（LLM，可空）
    status: InsightStatus
    first_seen: str
    last_seen: str
    pertains_to_version: str | None    # 针对哪个发布版本观测到
```

**聚合键 = `(workflow_definition_id, node_id, kind)`**：同一信号反复出现时 `occurrences++` + 刷新 `last_seen`，
不产生重复记录（"4 单卡在总经理"是 1 条 `occurrences=4` 的洞察，不是 4 条）。

## 3. 端口-适配器（沿用副驾那套 seam）

```
InsightWriter (port)   record(seed) → 幂等 upsert：按聚合键命中则累加，否则新建
InsightStore           聚合 + 持久化 + 生命周期（唯一实现）
InsightReader (port)   open_for(workflow_definition_id) → list[ProcessInsight]
```

- **写入方**只依赖 `InsightWriter`，不关心存储细节。
- **读取方**（设计 session）只依赖 `InsightReader`。
- 存储先落 SQLite 一张表即可（与 slice1 同库），不引消息队列。

## 4. 写入侧：两个 producer

### 4.1 OpsInsightProducer（运维臂，先做）
`ops_service.diagnose(instance)` 命中 `stuck_kind == "design_gap"` 时：
```
record(ProcessInsight(kind=COVERAGE_GAP, source=OPS,
        workflow_definition_id=<该实例所属流程>, node_id=<卡住环节>,
        evidence={"blocked_paths": [...], "case_no": ...}, severity="high"))
```
每张同因卡住的单命中一次 → `occurrences` 自增。这正是原型里"近 30 天 4 单卡在总经理审批"的来源。

### 4.2 AnalyticsInsightProducer（分析臂）
analytics 计算后，对 `detect_candidates(metrics)` 的每个 high/medium 候选：
```
record(ProcessInsight(kind=<candidate.kind 映射>, source=ANALYTICS,
        node_id=candidate.node_id, severity=candidate.severity,
        evidence=candidate.metric_reference, window="近30天"))
```
`headline` 复用 `process_analysis_agent` 已生成的归因文案（`DiagnosisItem`）。这是原型里"平均停留 3.2 天"的来源。

> 同一环节可同时有两条洞察（ops 的 coverage_gap + analytics 的 slow_node），banner 聚合展示。

### 4.3 什么内容反哺 · 什么时候触发（两道闸门 + 聚合 + 冒泡时机）

运维侧一个流程可能有几十条运维请求/记录，分析侧可能有多份报告——**绝大部分都不反哺**。
`record()` 不是无脑写：能到设计侧的内容，必须连过两道**确定性闸门**，再经聚合，最后按"冒泡时机"决定是否显现。

**核心纪律**：这个"蒸馏成几个问题点"的过程，是**确定性闸门 + 计数**做的，**不是让 LLM 读一堆原始记录去总结**
（那会漏、会编、不可控）。LLM 只给幸存下来的那条洞察写一句 `headline`。"什么值得反哺"始终由代码判定。

**闸门 1 · 这是不是"设计的问题"？（kind gate）**

| 来源信号 | 是否反哺 | 理由 |
|---|---|---|
| 运维 `design_gap`（覆盖漏洞·无路径） | ✅ | 确定的设计缺陷 |
| 运维 `data_error`（用户填错值） | ❌ | 用户的事，设计没错 |
| 运维 `org_gap`（岗位空缺，resolve_role 空） | 🟡 仅**反复**出现才反哺 | 一次性是排班问题；长期空=设计选了常年空的角色 |
| 运维 同一环节**反复被同类 override 批准** | ✅ | 反复的人工绕行 = 设计该把它固化 |
| 分析 越阈候选（`detect_candidates` 已筛） | ✅ | 慢过中位数 N 倍 / 退回 >35% / SLA <50% 才成候选，常规指标不出候选 |
| 分析 未越阈的常规指标 | ❌ | 没越线不打扰 |

**闸门 2 · 够不够严重/频繁，值得打扰设计？（materiality gate）**
- 硬缺陷（`design_gap`）→ **首次命中即冒泡**（但继续累计 `occurrences`）。
- 软/统计信号（慢环节、退回）→ 仅 `severity ∈ {high, medium}` 冒泡，low 不打扰。
- 避免"一次偶发就去烦设计"。

**聚合（去重）**：过了两闸的记录，按 `(workflow_definition_id, node_id, kind)` **合成一条** ——
N 条同 key 原始 → 1 条 `occurrences=N` + 关键数字。设计看到的是**一句话问题**，不是一堆原始对话/报告。

**冒泡时机 = 写触发 + 读触发两个时刻（producer 和 consumer 时间解耦）**
- **写（发现的那一刻）**：运维在 `diagnose()` 命中设计相关根因时写/累加；分析在**跑批**产出越阈候选时写。
  都是事件驱动的确定性写入，不是定时问 LLM"有啥要反哺"。
- **读（用到的那一刻）**：设计 session 打开该流程时 pull（just-in-time，见 §5）；
  流程管理 hub 加载时另显示一个轻量**「反哺提醒」计数**，让 Owner 进编辑器前就知道"这流程有 N 个待修点"。

**例（请假流程·某月）**：运维 10 条（5 data_fix + 1 withdraw + 4 design_gap）→ 只有 4 条 design_gap 反哺，
合成 1 条 `覆盖漏洞·occurrences=4`；分析全量 9 环节指标 → 只有 gm 越阈 → 1 条 `慢环节·3.2天`。
设计打开流程只看到 gm 环节上**两条蒸馏问题**，不是 10 条运维对话 + 一份指标 dump。

> `record()` 的调用点在 §4.1/§4.2，但真正写入前先过 4.3 的两闸；伪代码里的 `record(...)` 应理解为"过闸后的 upsert"。

### 4.4 运维臂实现架构：LangChain agent + 结算节点（**不用 LangGraph**）

现状：运维**不是** LangGraph——`decide()` 就是**一次** `structured_model.invoke()` 出 `OpsDecision`（单次结构化调用）。
要支持"诊断更丰富 + 留痕供反哺"，把单轮长成如下形态，但**仍不需要 LangGraph**：

```
[代码] 载入实例上下文（固定·grounding：condition_eval 求值每条出边 + resolve_role）
   │
[LangChain agent] 读诉求 →（按需调只读诊断工具）→ 终局输出结构化 OpsDecision
   │   只读工具 = simulate_path(假设值) / check_field_vs_rule / resolve_approver_at / explain_no_path …
   │   出决策 = 工具循环后 with_structured_output(OpsDecision)，或"提交决策"做成 schema=OpsDecision 的 tool
   │
[代码] 按决策执行（data_fix 即时应用 / override 建授权工单）
   │
[代码] 到达终局时「结算」→ 写一条 OpsIncident（供反哺）
```

**为什么不用 LangGraph**：整条链**只有一个 LLM 步**（那个 agent），其余全是确定性代码。LangGraph 是给
"多个 LLM/决策节点之间有状态/分支/中断"用的；这里够不上。基线其实连工具循环都不用——固定载入的上下文里
已有事实（路径求值/审批人），直接 `with_structured_output(OpsDecision)`（=现状）；只读工具只是"要假设模拟"等硬 case 的增强。

**只读 vs 写动作的纪律**：只读诊断工具（纯查询/计算、无副作用）让 LLM 自由调**安全**；写动作（jump/skip/reassign）
**仍走 structured OpsDecision + 人确认**，不给 LLM 自动执行。

**结算节点（OpsIncident）**：不是 LLM 步、不是"决策后的顺序节点"，而是**生命周期驱动的确定性 service 结算**——
data_fix 即时结算，override 在 owner 批准的**那次后续请求**里才结算。它写的对象是 **OpsIncident**（比 OpsDecision 完整）：

```python
class OpsIncident:            # 运维交互终局时固定写一条（原始事件底料）
    incident_id; instance_id; workflow_definition_id; node_id
    diagnosis_snapshot        # 诊断快照：哪些出边 dead、approver 状态、只读工具输出
    ops_decision              # OpsDecision（category + grounded field/node + rationale）
    resolution                # 终局处置：data_fix_applied / override_authorized / denied / escalated
    unblocked                 # 处置后是否真走通
    derived_kind; channel     # 由 (diagnosis + resolution) 确定性映射
    timestamp
```

**处置路径本身是确定性分类器**：`data_fix 改完就走`→数据/操作（反复同字段→design）；`试遍合理值都不走只能 override`→design_gap；
`deny`→policy；`escalate`→triage。这张映射表固定、代码判。

**两层存储**：OpsIncident（每单一条，原始统计/审计底料）→ InsightWriter 读它、过 §4.3 两闸 + 按 key 聚合 → ProcessInsight（蒸馏、供反哺）。
`OpsDecision` 只是 OpsIncident 的一个字段，**不足以单独当分析对象**。

### 4.5 分析臂实现架构：workflow（报告）+ agent（问答），都是"结构化提案 + 代码执行"

分析侧现状：两块**都不是 LangGraph、也不是 tool-calling agent**，都是**单次 `with_structured_output().invoke()` + 确定性代码**
（`process_analysis_agent`、`analytics_query_agent` 均如此）——和运维、设计编辑同一条脊柱：**LLM 出结构化提案，代码确定性执行**。

**分析侧是两种形态,不是二选一:**

| | 诊断报告 | 指标问答 |
|---|---|---|
| 形态 | **workflow(pipeline)** | **agent(对话)** |
| 触发 | 主动跑批(无需用户) | 交互(用户问) |
| 逻辑 | `compute_metrics`(确定性)→ `detect_candidates`(确定性)→ 一次 LLM 归因 → 组装 | LLM 出 `AnalyticsQueryProposal`(结构化)→ 代码执行查询 → 答 |
| 框架 | plain pipeline（线性、就一个 LLM 步，**不用 LangGraph**） | 结构化提案+代码执行（**不用 tool-calling、不用 LangGraph**）；要多轮迭代则扩成**有界结构化循环**，仍不改框架 |

> 命名提醒：`process_analysis_agent` 虽叫 "agent"，逻辑其实是 **workflow 形态**（LLM 只做归因、不自主调工具）。真正的交互 agent 是 `analytics_query_agent`。

**与运维不对称的点**：运维只有 agent（永远被用户触发）；分析多一个 **workflow**（能主动跑批诊断）。这是"分析能直接诊断、运维要有人撞上"的实现体现。

**两条反哺路径（都无人确认，都代码验证）：**
- **诊断报告的 `CandidateBottleneck`** → 天生结构化 → **自动**进反哺（过 §4.3 两闸 + 聚合）。
- **指标问答里发现的疑似问题** → 见下方触发机制，**代码重跑验证后**进反哺——**不走人确认**（对话用户/owner/管理员都不该当"是不是问题"这道闸；是不是问题由**代码重跑查询比阈值**判定）。

**指标问答的反哺触发机制**：给 `AnalyticsQueryProposal` 加一个可选字段——

```python
class GroundedCheck(BaseModel):        # 一个"可被代码重跑验证的假设"
    node_id: str | None
    metric_kind: Literal["slow_node","return_rate","sla_breach","dead_node", ...]
    segment: dict | None               # 如 {"dept":"财务"}——固定检测器没覆盖的分段/维度
    window: str

class AnalyticsQueryProposal(BaseModel):
    answer_query: QuerySpec                      # 回答用户这轮问题（现有）
    suspected_issues: list[GroundedCheck] = []   # 🆕 LLM 顺手标记的"疑似问题"（可空）
```

一轮流程：用户问 → LLM 出 `{answer_query, suspected_issues:[...]}` → 代码执行 `answer_query` 答用户；
**代码逐个重跑 `suspected_issues` 的查询 → 拿确定性数字 → 套 `thresholds.py` 阈值：越阈→构造反哺候选(node/kind/severity/evidence)→过闸聚合 emit；没越→丢弃。**

**纪律**：LLM 出的是**可验证的假设**（grounded 查询规格，召回），**反哺与否由代码重跑验证决定**（精度），不是 LLM 拍板、更不是人确认——与运维"LLM 抽 grounded 结构 → 代码验/计数"完全对称。
**边界**：化不成可执行检查的（纯定性，如"这流程感觉绕"）→ 填不出 `GroundedCheck` → **不进反哺**，最多当条备注；**验不了的不驱动设计改动**。
**加分**：某个 `suspected_issue` 反复被验证命中 → **提升为 `thresholds.py` 常驻检测器**（对话是"新检测器的孵化器"）。

> 澄清 vs §7 的 `triage`：**"是不是问题"永远由代码验证**（本节），**从不靠人**；§7 的 `triage` 只处理"某个**已确认**问题的根因二义（design or 资源）该归哪个 channel"——那是渠道归属、且本期只作展示分类，不是"是不是问题"那道闸。

## 5. 读取侧：回流给设计

**打开设计 session 时**（`create_or_open_session`）：
1. `InsightReader.open_for(wf_id)` 取该流程所有 open/acknowledged 洞察。
2. 注入 `design_edit_agent` 的 prompt（**retrieve-then-read**：代码检索 → 注入 → LLM 引用），
   使副驾能说"运行侧有 N 条证据建议改这里"，但**不自动改**，仍是提议→人确认。
3. `session_payload` 带上 insights → 前端渲染：
   - 工作台顶部 **「运行侧回传 banner」**（原型已画）
   - 对应环节卡的 **「N 条运行证据」** 角标（原型已画）
4. 洞察作为一类新的"运行证据待办"，与 `business_validation` 的 `UserClarificationRequest` 并列在待确认区。

## 6. 闭环收口：修订后确定性复检 → 洞察消解

这是"反哺"能被**度量**的关键，也是最漂亮的一环：**洞察由确定性检测生成，就由同一检测复检消解**。

- 每次 `confirm_pending_edit` / 生成新版本后，对本流程 open 的洞察跑复检：
  - `COVERAGE_GAP`：用 `condition_eval` 复评该区间是否已有路径 → 有则 `status=RESOLVED`。
  - `SLOW_NODE / HIGH_RETURN`：改了设计不等于运行变好——先置 `ACKNOWLEDGED`，等**新版本上线跑一段**、
    AnalyticsInsightProducer 下一轮复算不再命中阈值时才判 `RESOLVED`。这才是真闭环（改→上线→再观测→消解）。
- `RESOLVED` 的洞察进入 **版本对比**「改进前后」：量化"补齐 4–7 天档后，卡滞 4 → 0"，正是原型版本对比 tab 的内容。

## 7. 广义化：多渠道分诊（运行=问题暴露层）

运维/分析是问题的**暴露点**，但暴露的问题不全是设计缺陷——也可能是制度、组织、数据、资源问题。
「反哺设计」只是其中一条渠道；其余问题不该被丢弃，而应**按渠道分类**，给出各自的归宿。
`ProcessInsight` 加一个 `channel` 字段承载这层路由：

| `channel` | 根因 | 处置渠道（愿景） | 触发升级的信号 |
|---|---|---|---|
| `design` | 设计缺陷 | 设计工作台 | 覆盖漏洞、反复被 override 的绕行、**反复**同类 data_error（字段诱导错填） |
| `policy` | 制度/政策 | 流程 owner + 制度与规则库 | 口径反复被澄清、规则冲突、制度过时 |
| `org` | 组织/排班 | 部门 / HR | 某角色**长期**空缺（resolve_role 反复空） |
| `data` | 数据/字段 | 一次性=发起人；反复→升 `design` | 个别填错 |
| `ops` | 运营/资源 | 运营 | 人手不足致慢（非设计问题） |
| `triage` | 拿不准 | 待流程 owner 人工分诊 | 慢环节（设计 or 资源分不清）——确定性检测器判不了的，交人 |

**确定性边界**：能确定根因的自动落 `channel`（`design_gap`→design、长期 `org_gap`→org）；判不清的落 `triage`，
由 owner 人工定（可选 LLM 建议渠道、owner 确认）。判断题交给人，不让 LLM 硬判。

**这样是三个环，不是一个**：运行→设计、运行→制度（"制度反复被澄清 → 建议更新原子规则"，直接喂模块 3 规则 RAG）、
运行→组织。运行侧从"卡单处理台"升级为"全组织问题传感器 + 分诊中枢"。

### 7.1 本期范围（重要 · 收窄）

本系统**不是真实 OA**，没有对接真实的流程 owner 工单、HR、制度维护流程。故本期：
- **`design` 渠道：走完整闭环**（暴露 → 反哺设计工作台 → 修 → 复检消解）。这是唯一"真解决"的渠道。
- **其余渠道（policy/org/data/ops/triage）：只做"暴露 + 分类展示"**，不做真实路由/派单。
  即：在**流程管理**里把这些问题按 `channel` 分类列出来给 owner 看见，但不真的通知 HR、不真的改制度库、不真的建工单。
- 真实路由（派单给 owner/HR、写回制度库）= **愿景/后续**，等系统接入真实 OA 能力再落。

**落地增量**：`ProcessInsight` 加 `channel`（+ 可选 `assigned_owner`/分诊 `status`）；
设计工作台 banner 只查 `channel=design`；流程管理卡片显示**全渠道分类计数**（见 §7.2 UI）。
"全局复盘区"是在现有 InsightStore 上按 owner 过滤的**一个视图**，不是新存储。

### 7.2 UI 接入：流程管理卡片的「运行反馈」

每张流程卡增加一块**运行反馈**：分渠道显示待处理问题数（设计 N / 制度 M / 组织 K / 待分诊 T）。
- `design` 类：可点 → "去工作台修复"（进设计工作台，banner 已在等）。**唯一可操作**。
- 其余类：**只暴露 + 分类展示**（本期不可路由），点开看详情/证据，标注"暂不支持自动派单"。
- 卡片顶部一个总计红点（如"3 个运行反馈待看"），Owner 进编辑器前就知道这条流程有账要还。

## 8. API 与前端接入点

- `GET /api/v1/insights?workflow_definition_id=xxx&status=open` —— 供 流程管理「反哺提醒」+ 工作台 banner。
- 设计 `session_payload` 内嵌 `insights` 字段。
- producer 由 analytics/ops 内部直接调用 `record()`，不必走外部 HTTP。

## 9. 分期落地

- **P0**：`ProcessInsight` schema + `InsightStore`（幂等 upsert + 生命周期）+ 单测。
- **P1（单臂即可演示闭环）**：OpsInsightProducer(coverage_gap) + 设计读取（session 注入 + banner + 环节证据角标）。
  Demo：inst_gap 反复卡 → 累计 `occurrences=4` → 打开请假流程 → banner + gm 环节「4 条运行证据」→
  「把 4–7 天并入更高一档」→ confirm → `condition_eval` 复检该区间已有路径 → 洞察 RESOLVED。
- **P2**：AnalyticsInsightProducer(bottleneck) —— 补上"分析→反哺"臂（3.2 天停留 → slow_node 洞察）。
- **P3**：生命周期 RESOLVED 自动化（复检）+ 版本对比量化"改进前后"。

## 10. YAGNI / 边界

- 不做实时流；洞察在 analytics 跑批 + ops 诊断时产生。
- 不做 ML 排序；severity 走 thresholds 确定性判定。
- 不做跨流程聚合大盘；先按单流程。
- headline 可先模板兜底（无 LLM 也能跑），LLM 措辞是增强不是前置依赖。
- 不改两端既有产出结构，只**新增**一个 writer 调用 + 一个 reader 注入点，侵入最小。
