# 流程参与者 AI 副驾 · 设计文档

> 状态：设计（未落码）。定位这是继"设计 Agent + 规则 RAG + 分析闭环"之后的第四条纵向。
> 三个 agent 覆盖流程生命周期的三个触点，共享一层"实例接口"地基。

---

## 0. 一句话

**给流程的三类参与者各配一个 AI 副驾**——发起前（选流程/预演路径）、卡住时（运维异常 override）、办理中（在办任务提醒/问答/协助）——它们**只跟一层抽象的"实例接口"对话**，因此不碰已冻结的 OA 运行时，且未来可对接飞书或真实引擎。

---

## 1. 背景与定位

现有四模块闭环已在**引擎A 的 canonical 模型 + 合成数据**上做通：AI 设计流程 → 上线流转（薄运行时，冻结）→ 运营分析 → 优化反哺。分析侧、规则 RAG、合规拦截都已落地。

这条新纵向补的是**"流程运行期，人的那一侧"**——真实业务里，流程上线后大量成本不在流程本身，而在**参与者与流程的交互摩擦**：不知道走哪个流程、被流程逻辑卡死、在办任务堆积无人提醒。这些都是作者在实际业务中亲历的痛点，且**通用产品很少做深**。

### 生命周期三触点

| 触点 | Agent | 典型诉求 |
|---|---|---|
| **发起前** | #4 发起问答副驾 | 我这情况该走哪个流程？会经过哪些环节？我符合条件吗？ |
| **卡住时** | #3 运维副驾（旗舰） | 选不到人/没有满足的路径，能不能跳环节/跳过/撤回？ |
| **办理中** | #2 在办任务副驾 | 这单卡了几天了、有没有踩制度红线、材料缺不缺、帮我处理 |

三者是**同一套架构的三个实例**，优先级 **#3 > #4 > #2**（差异化 × 复用资产 × 成本）。

---

## 2. 核心架构决策：端口-适配器（实例接口）

### 2.1 问题

每个副驾都要"从流程实例读信息 + 把动作写回实例"。若直接依赖 OA 运行时，就会重新扩张那块**已冻结**的重运行时；而当前测试环境也没有真实的、带丰富时间/路径分布的实例。

### 2.2 决策

引入一层**抽象实例接口（Instance Port）**，把 **agent 逻辑（价值）** 与 **运行时引擎（可插拔底座）** 解耦（hexagonal / ports-adapters）：

```
        ┌─────────────── Agent 逻辑（本纵向的价值）───────────────┐
        │  #3 运维副驾    #4 发起问答副驾    #2 在办任务副驾        │
        └──────────────────────┬──────────────────────────────────┘
                               │ 只依赖抽象接口
                    ┌──────────▼───────────┐
                    │   Instance Port      │  输入契约 + 输出契约
                    └──────────┬───────────┘
             ┌─────────────────┼───────────────────┐
        ┌────▼────┐      ┌─────▼─────┐        ┌─────▼─────┐
        │  Mock   │      │ OA 运行时  │        │  飞书审批  │
        │ (现在做) │      │(降级为一个 │        │ (未来适配) │
        │         │      │  adapter) │        │           │
        └─────────┘      └───────────┘        └───────────┘
```

**关键推论**：
- 三个副驾**当下全部基于 Mock adapter 开发**——不碰流转，纯 agent 逻辑。
- OA 运行时**不删，降级**为该接口的一个实现；它给 demo 提供"有个东西代表在办任务"的具体载体。
- 飞书、真实引擎是未来的另外两个 adapter，接口不变。

### 2.3 输入契约（agent 从实例读什么）

一个只读快照 `InstanceContext`（Mock 造、未来由 adapter 填）：

```
InstanceContext:
  instance_id
  process_definition        # 复用现有 ProcessDefinition
  current_node_id / name
  form_values               # 用户已填的表单值
  history                   # 已流转的环节 + 处理人 + 动作 + 时间戳
  # —— 供 #3 诊断"为什么卡" ——
  path_evaluations          # 每条 submit_path 的 condition 求值结果（哪条通/为什么被卡）
  approver_resolution        # 各环节 resolve_role 结果（谁能审 / 为空的原因）
```

### 2.4 输出契约（agent 能对实例做什么）

一个**受限动作集** `InstanceAction`（typed，判别联合），由确定性代码校验+应用（Mock 下就是打印/改内存快照）：

```
InstanceAction（判别联合，op 区分）:
  jump_to_node(target_node_id)         # 跳到某环节
  skip_current_node()                  # 跳过当前环节
  withdraw()                           # 撤回
  reassign_approver(node_id, user)     # 改派审批人
  update_field_value(field_name, value)  # 修改实例上的表单字段值
  answer_only(text)                    # 仅答复、不改实例（#4 常用）
```

`update_field_value` 是运维/在办场景里的高频诉求——很多"卡住"根源不是流程设计有洞，而是**字段填错**（比如请假天数填错导致算不出满足条件的路径；或在办环节需要补全/更正一个值再继续走）。它跟设计期的 `UpdateFormField`（[process_edit_tools.py](../app/tools/process_edit_tools.py)）是同一个模式在**实例层**的对应物，但语义不同：设计期改的是 `ProcessDefinition.form_fields` 的**定义**（校验规则、默认值等），这里改的是**某个实例上该字段的当前取值**。

**确定性校验**（应用前，非 LLM 判断）：
- 字段必须存在于 `process_definition.form_fields`（否则拒绝，不臆造字段）
- **`allow_stage_override` 开关**（实现时发现的必要区分）：字段的 `editable_stages` 本来管的是"普通用户在标准 UI 上能不能编辑"——但运维本来就有权在非 draft 环节改数据（现实里这正是运维区别于普通用户的地方），所以 #3 调用时传 `allow_stage_override=True`，跳过这层限制；#2 在办副驾"协助用户编辑自己的表单"走的是普通用户权限，保持默认 `False`、照常遵守 `editable_stages`。同一个动作、同一份校验代码，靠一个显式参数区分两种权限语境，不用为两个副驾分叉出两套动作。
- 新值的类型/格式应与 `component_type` 基本相容（如数字字段不能填非数字）——这一步做成轻量校验即可，不追求和设计期合规校验一样重

**心法一致（全项目贯穿）**：agent 只输出**判断/意图**，动作的**合法性与应用由确定性代码兜底**（目标环节是否存在、跳转是否结构合法、字段是否可编辑）；规则没覆盖就**升级人工**——复用你已建的 confirm/discard 拦截 UI 哲学（[workflow_design_service.py:823](../app/api/workflow_design_service.py) 的 `confirm_pending_edit`/`discard_pending_edit`）。

## 3. #3 运维副驾（旗舰）

### 3.1 场景（真实痛点）

复杂流程必有边际 case / 逻辑漏洞。用户提交后被卡，根因通常是下面三类之一：
- **没有满足的路径**（设计缺口）：所有 submit_path 的 condition 都不成立（用户场景没被任何一条覆盖）
- **选不到人**（组织缺口）：某环节 `resolve_role` 解析为空（组织里没有对应角色/该岗位空缺）
- **字段填错**（数据问题，非设计缺口）：路径设计本身没问题，但用户填的值不对（比如请假天数手滑填成 6 而不是 7），导致算出来"卡在这"——这种只需**纠正字段值**，流程会自己按原设计的路径走下去，根本不需要 override

用户于是找**人工运维团队**。运维先判断是不是"填错了"这种低风险情形，若是就直接改字段；若真是设计/组织缺口，再依据**流程 owner 提供的规则**或**运维团队自己的通用规则**，判断能否按用户诉求**跳到某环节 / 跳过当前环节 / 撤回 / 改派**。**这套判断可由 agent 替代。**

### 3.2 决策逻辑

```
1. 诊断"为什么卡"（确定性，非 LLM）
   - 对每条 submit_path 跑 evaluate_condition（app/runtime/condition_eval.py）
     → 列出：哪条本可走、哪条被卡、被哪个子条件卡、差多少（如天数差1天）
   - 对当前/目标环节跑 resolve_role（app/org_knowledge.py）
     → 审批人是否为空、为空的原因
2. 优先检验"是不是数据问题"（低风险、优先尝试，不需要 override 授权）
   - 结合用户诉求判断：用户是在说"这个值应该是 X"，还是在说"我要绕过这条规则"？
   - 若是前者 → 校验字段存在 + 当前环节可编辑 → 产出 update_field_value，
     不动流程结构，路径按原设计自然重新求值
3. 若确认是设计/组织缺口 → 取适用的 override 规则（规则 RAG）
   - owner 针对该流程的 override 规则 + 运维团队通用规则
   - 复用 app/rag/rules.py + index.py（结构化预筛 ∪ 语义召回）
4. Agent 研判（LLM 只做判断，不做执行）
   - 用户诉求（跳到X / 跳过 / 撤回 / 改派）是否被规则允许？
   - 输出：准（引用规则）/ 驳（说明理由）/ 升级人工（规则未覆盖）
5. 确定性校验 + 应用（Mock adapter）
   - 目标环节是否存在、跳转是否结构合法、字段是否可编辑 → 非法直接拒，不臆造
   - 合法则产出 InstanceAction，由 adapter 应用
```

第 2 步刻意排在 override 判断**之前**：数据纠错比结构性 override 风险低得多（不改变流程走向，只是让原设计正确生效），所以 agent 应该先排除"是不是填错了"，而不是一上来就假设需要破例。

### 3.3 复用了什么（几乎全是你已有的）

| 步骤 | 复用现有组件 |
|---|---|
| 为什么卡（路径） | `app/runtime/condition_eval.py` `evaluate_condition` |
| 为什么卡（人） | `app/org_knowledge.py` `resolve_role` |
| override 规则 | `app/rag/rules.py` + `index.py`（规则 RAG） |
| agent 研判 | 仿 `compliance_judge_agent` / `design_edit_agent` 的 typed 结构化输出 |
| 动作合法性 | 仿 `apply_edit_operations` 的"找不到引用就报错不臆造" |
| 字段可编辑性校验 | 复用 `FormField.editable_stages`（同一份 ProcessDefinition schema） |
| 升级人工 | 仿 confirm/discard 拦截 |

### 3.4 为什么它是旗舰

真实且具体的运营痛点 + 差异化极高（"AI 运维处理流程异常"几乎无人做 demo）+ 深度复用你全部资产 + 靠 Mock-I/O 完全不需要真流转。**一句话最能证明"你懂真实运营 + 会用 AI 确定性地解决"。**

### 3.5 Mock 造什么

构造几个"卡住"的 `InstanceContext`，覆盖三类根因：
- **设计缺口**：请假 6 天，但所有路径 condition 都要求 >7 天或 ≤3 天（区间漏洞）→ 需 override（跳转/跳过）
- **组织缺口**：某审批环节 `resolve_role` 返回空（岗位空缺）→ 需改派
- **数据问题**：请假天数字段填成 6，实际应为 8（走到条线分管领导才对）→ 只需 `update_field_value` 纠正，不需要任何 override

这三类是**可确定性构造**的边际 case，正好展示诊断能分清"什么时候不需要破例、只需要改数据"。

## 4. #4 发起问答副驾（快赢搭档）

### 4.1 场景
用户发起前不知道：该走哪个流程 / 我这情况会经过哪些环节 / 我符不符合条件。

### 4.2 特点
- **纯只读**，完全不碰实例（`InstanceAction` 只用 `answer_only`）——**成本最低**
- 几乎 100% 复用现有资产：流程定义 + 规则 RAG + `KnowledgeService`

### 4.3 决策逻辑
```
1. 理解用户处境（LLM 解析自由文本 → 结构化属性，如 请假类型/天数）
2. 召回候选流程定义 + 适用性规则（规则 RAG）
3. 路径预演（确定性）：用 evaluate_condition 拿用户属性跑一遍 submit_paths
   → "按你的情况(请假10天)，会走：起草→主管→总经理→条线分管领导"
4. 资格判定：按规则回答"你是否需要/符合"，有据引用（诚实空：无据不编）
```

**亮点**：第 3 步用 `condition_eval` **拿用户的假设属性预演真实路径**——这不是泛泛问答，是扎在真实流程定义 + 规则上的"路径模拟器"，比通用"问该用哪个表单"高一个身位。

## 5. #2 在办任务副驾（须"蹭资产"才做）

### 5.1 陷阱
工作台上放个通用 AI 助手问答 = 平庸，满大街都是。**只有绑定你的独有资产才值得做。**

### 5.2 三个子能力（都必须蹭资产）
- **AI 提醒（主动）**：这单卡了 N 天（分析）/ 踩了制度红线（合规引擎）/ 材料缺失（规则 RAG）
- **AI 问答（被动）**：就这单在办任务提问，答案扎在该流程定义 + 适用规则上
- **协助处理**：解释当前环节可选动作、帮拟处理意见；发现字段填得不对/不全时，产出 `update_field_value` 帮用户改好（同一个动作，#3 用来纠正阻塞、这里用来提升在办效率）

### 5.3 与 OA 运行时的关系
在办任务 = `InstanceContext`（Mock）。**工作台待办查看功能弱化**（那是冻结底座、非差异点），但**不删**——它作为 Instance Port 的载体，给"有个在办任务"提供具体着陆点。

| 组件（已有） | #3 运维 | #4 发起问答 | #2 在办 |

| ProcessDefinition | ✅ | ✅ | ✅ |
| condition_eval（路径求值/预演） | ✅ | ✅ | – |
| resolve_role（选人诊断） | ✅ | – | – |
| 规则 RAG（rules + index） | ✅ | ✅ | ✅ |
| 合规引擎（compliance） | – | – | ✅ |
| 分析（堵点/耗时） | – | – | ✅ |
| typed-agent 结构化输出范式 | ✅ | ✅ | ✅ |
| confirm/discard 人工兜底 | ✅ | – | ✅ |

**新增的只有**：`InstanceContext`/`InstanceAction` 契约 + Mock adapter + 三个 agent 的 prompt/决策编排。运行时零扩张。

## 7. 落地分期

- **地基（半天）**：定义 `InstanceContext` / `InstanceAction`（放 `data/schema/` 或 `app/runtime/ports/`）+ Mock adapter。
- **Phase 1 — #3 运维副驾**：诊断（condition_eval + resolve_role）→ 规则 RAG 取 override 规则 → judge agent → 确定性校验动作。构造 3-4 个卡住 case + 评测（判对率）。
- **Phase 2 — #4 发起问答**：只读，复用 RAG + 路径预演。
- **Phase 3 — #2 在办副驾**：绑定合规/分析/RAG 的提醒 + 问答。

每期都有确定性可评测的靶子（#3 override 判对率、#4 路径预演准确率），延续你"评测驱动"的一贯做法。

---

## 8. 边界与 YAGNI

- **不碰真流转**：全部基于 Mock adapter；OA 运行时降级不删；飞书/真实引擎是未来 adapter。
- **不做通用 AI 助手**：#2 不蹭资产就不做。
- **agent 不执行、只判断**：动作合法性与应用永远是确定性代码；规则未覆盖就升级人工。
- **只读优先**：#4 纯只读先行，验证"参与者副驾"价值后再上有副作用的 #3/#2。

---

## 9. 面试可讲的点（这份设计本身就是叙事）

1. **端口-适配器解耦 AI 与运行时**：agent 逻辑不锁死在任何引擎，Mock/OA/飞书可插拔——体现架构判断力。
2. **AI 运维异常处理**：一个通用产品少见、但真实业务高频的痛点，且用"确定性诊断 + 规则 RAG + agent 研判 + 代码兜底 + 人工升级"这套组合拳解决——体现对真实运营的理解。
3. **生命周期副驾套件**：发起前/卡住时/办理中三触点一套架构，体现产品结构化思维。
4. **一贯的确定性纪律**：LLM 判断、代码执行、无据不编、规则未覆盖升级人工——贯穿全项目。
