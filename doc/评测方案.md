# Agent 评测方案

> 目标：给系统每个**功能模块**建立可复现、可回归、可对外解释的评测。
> 原则跟工程主张一致——**确定性归确定性、LLM 归 LLM**：
> 「一次交互算不算成功」必须由**确定性系统状态**判定，绝不问 LLM"你解决了吗"。

---

## 一、组织原则：主轴是功能模块，不是 LLM 决策点

评测单元要跟**用户能感知的能力**对齐，而不是跟内部实现结构对齐。

反例：`business_validation` 是设计管线 LangGraph 里的一个**节点**
（`source_file_loader → source_context_builder → process_extraction_agent → structural_validator
→ business_validation → output_writer`，带重试回边），不是独立 agent。
把它抠出来单独打分没有意义——它的"对"只能相对**管线端到端产出**定义。
正确做法是评整条管线的输入→输出（`process_target_eval`，**已落地**）。

因此分两层，**职责不同、不可互相替代**：

| 层 | 回答什么问题 | 面向 | 单位 |
|---|---|---|---|
| **模块级端到端** | 这个能力**好不好用** | 对外 / 产品 | 一次完整任务（可能多轮） |
| **诊断层** | 出问题时**错在哪** | 对内 / 可定位 | 单次决策 / 单个组件 |

只有模块级：解决率掉了不知道为什么；只有诊断层：组件都 90% 但用户照样办不成事。
**诊断层归属到各模块之下**，不自成体系。

## 二、判定「成功」的确定性判据（本方案的地基）

多轮任务评测最容易做成自欺的地方，就是让模型自评是否解决。本系统的优势是
**每个模块的"成功"都能锚在系统状态变化上**，无需人工判断：

| 模块 | 确定性成功判据 | 成本指标 |
|---|---|---|
| 运维 | 实例 `status`：**stuck → flowing / completed** | 轮次、是否需授权 |
| 设计 · 初始化 | 产出通过结构校验的定义，且对 gold 打分 | 抽取分 |
| 设计 · 会话式修改 | 草稿 → **PUBLISHED** | **上架前编辑轮次** |
| 发起向导 | 用户**真按推荐流程发起**了 | 轮次 |
| 效能分析 | 产出**被采纳**的反哺洞察 | — |
| 流程管理 | 路由后**无重问** | — |

## 三、使能器：模拟用户 harness（多轮评测的前提）

单轮评测喂一句话即可；**解决率 / 轮次**需要完整会话轨迹。做法：
LLM 扮演一个**有明确目标**的角色（"我这单卡住了，我要它能继续走"），
对着**真实系统**多轮交互，直到确定性判据触发或超过 N 轮才停。

产出：`成功/失败 · 轮次 · 走过的 route 分布 · 触发的护栏`。

> 这同时回答了"没上线、缺业务数据怎么评"——**模拟用户 + 确定性判据 = 无需真实用户即可跑出解决率与轮次分布**。
> 代价：这是本方案里最重的一块，明显重于断言层。

## 四、五个功能模块

### 4.1 设计 Agent

用户：流程 owner。有**两个评测面**，性质不同，必须分开。

#### ① 初始化（LangGraph 批处理管线）— ✅ 已落地

- **一次成功** = 多源材料 → 通过结构校验的标准流程定义。
- **端到端指标**：要素级 P/R/F1 加权总分 vs 人工 gold（`app/eval/process_target_eval.py`）。
  当前基线（`doc/eval_summary.md`）：EOA140 **95.25** · 请假 **90.71** · 报销 **80.0** · 均值 **88.65**。
- **诊断层**（解释总分为什么动，不单独设门槛）：
  - `business_validation` 节点触发的**重试轮数**、**误 blocking 率**（把本该 warning 的判成 blocking）；
  - `structural_validator` 的 `schema_errors` 类型分布；
  - 澄清项（clarification）召回。
- **数据**：已有 gold（`data/cases/*/standard/target.json`）。

#### ② 会话式修改（多轮）— 待建

- **一次成功** = 用户口述的修改意图被正确落到草稿，最终 **PUBLISHED**。
- **端到端指标**：改对率、**上架前编辑轮次**（⭐ 比抽取分更能说明"是否真省力"）、
  撤销/返工率（用户 undo 的比例）。
- **诊断层**：指令 → 编辑操作序列的字段级 P/R/F1（可复用 `process_target_eval` 打分器）；
  `out_of_scope` 判定准确率；**reply 与 operations 一致性**（见横切层）。
- **数据**：模拟用户（给定"把 X 改成 Y"的目标）+ 确定性 diff 校验。

### 4.2 运维 Agent

用户：发起人 / 审批人 / 管理员。**风险最高**（会改流程走向），也是最该做多轮解决率的模块。

- **一次成功** = 卡住的单子恢复流转：`status` **stuck → flowing / completed**。
- **端到端指标**：
  - **卡单解决率**、**平均解决轮次**；
  - route 分布：自助终局 / 转授权 / 升级人工；
  - **高风险动作误放行 = 0**（安全硬指标，绝对值不是比例）；
  - 授权后**执行成功率**（批准了但被确定性校验拦下的比例）。
- **诊断层**：11 类 `category` 分类准确率（混淆矩阵）、`target_node_id` 选对率、
  `deny` vs `escalate` 判别、规则引用正确率。
- **数据**：现有 mock 实例已覆盖多种卡因（覆盖漏洞 / 选不到人 / 材料缺失），
  模拟用户扮演发起人即可跑；**判据完全确定性**。

### 4.3 效能分析 Agent

用户：流程 owner / 全局管理员。检出能力本就是确定性的，LLM 只写归因。

- **一次成功** = 问题被检出**且**产出被采纳的优化建议。
- **端到端指标**：
  - 堵点检出率 / 误报率（`app/eval/detection_eval.py`，**已落地**，还区分"二级连带"与"真误报"）；
  - **建议被采纳率**（⭐ 反哺闭环里 adopted 占比，衡量闭环是否真闭上）；
  - 指标问答的**答案数值正确率**（可拿合成事件数据**确定性验算**，不用人判）。
- **诊断层**：取数升级正确率（L1 快照 / L2 typed / L3 SQL 该用哪级）、
  SQL 护栏拦截率、归因文案质量（LLM-judge + 人工抽检，软指标）。
- **数据**：已有注入病灶清单当 gold；数值类可验算。

### 4.4 发起向导 Agent

用户：普通员工。只读、无副作用，风险最低。

- **一次成功** = 用户按推荐的流程**真的发起**了申请。
- **端到端指标**：流程推荐准确率、**路径预演一致率**（预演路径 ≡ 实际流转路径）、轮次。
- **诊断层**：槽位抽取（请假类型 / 天数）准确率、无依据时是否老实说"问 HR"（**不编造率**）。
- **数据**：话术标注集 + 确定性路径预演比对（`preview_path` 本就是确定性的，可当 gold）。

### 4.5 流程管理 Agent

用户：流程 owner / 系统管理员。本质是**路由 + 编排**，不产出业务结论。

- **一次成功** = 路由到正确能力**且**下游答对，用户**不重问**。
- **端到端指标**：路由准确率（≈ 模块指标本身）、**重问率**、跨流程比较类问题的答对率。
- **诊断层**：7 类 route 混淆矩阵、`target_workflow_id` 选对率（含"该留空时真留空"）。
- **数据**：话术标注集（每类约 20 条，AI 造 + 人工定标）。

> 注：这个模块的模块级指标几乎完全分解成路由准确率，不必硬套"解决率"。

## 五、横切层：一致性 / 护栏断言 — ✅ 已落地

> `app/eval/consistency_eval.py` · `tests/test_consistency_eval.py`（15 例）
> 入口：`uv run python scripts/run_consistency_eval.py`

这层**跨所有模块**，评的不是"答得准不准"，而是"输出内部自不自洽、有没有泄漏实现、有没有编造依据"——
**无参照断言**，对单条输出本身即可判对错，**不需要 gold**。

| 断言 | 判什么 | 对应真实修过的 bug |
|---|---|---|
| `say_do_target` | 文案点名的环节 ≡ 实际跳转目标 | 说"跳条线分管领导"、动作却填"起草" |
| `route_promise` | 承诺兑现（承诺转授权 ⟹ route 真是 authorization） | 承诺授权、实际静默 escalate |
| `identifier_leak` | 可见文案 ∌ `u_xxx` / `node_id` / `override` | 工作交接人显示 `u_it_line_leader` |
| `ungrounded_citation` | 引用的规则 id ∈ 知识库 | 防编造条款 |

**设计要点：评的是架构保证，不是模型能力。** 夹具**故意构造"LLM 胡说"的决策**
（reply 说跳 A、`target_node_id` 填 B；承诺授权却改派给不存在的人），
断言**确定性层能不能把矛盾中和掉**——中和不掉才算失败。因此不打 Bedrock、不随模型波动、可进 CI。

跟 `compliance_eval` 同纪律：每 case 声明期望断言，既量漏检也量误报；其中一条是**正控**
（rationale 直写 `node_id`），证明检测器有效而非摆设。

当前结果：`case 4 · 检出率(正控) 1.0 · 误报 0 · 干净基线 3`。

> 首次运行即发现真问题：escalate 兜底文案写着"请在运维授权台…补充"，
> 但看到它的是**发起人**，无权在授权台操作。已修。

**硬性指标（必须为 0）**：说到做到率 100% · 标识符泄漏 0 · 编造引用 0。

## 附：几条容易走偏的地方

1. **别把 LangGraph 内部节点当评测对象**——`business_validation`、`structural_validator`
   这类节点只有相对管线产出才有"对错"，单独打分会引导出错误的优化方向（如让它少报 blocking
   来"提分"，实际损害端到端质量）。它们的指标只作**诊断**用，不设门槛。
2. **别让 LLM 自评是否解决**——一律锚在系统状态变化上（第二节）。
3. **别只看解决率**——要同时看**轮次**和**route 分布**。解决率 100% 但全靠"升级人工"，
   等于没有自动化价值。
4. **诊断层不设对外 KPI**——它是定位工具。对外只报模块级指标 + 横切硬性指标。
